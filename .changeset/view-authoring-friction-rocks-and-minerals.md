Five things that tripped a chat writing worker views for a children's rocks-and-minerals app now work as an author expects (Roadmap f-view-authoring-friction-2026-11).

A view of one record reads its own kind across a relation back to it. A rock's page that read `becomes` (rock → rock) was handed no linked rock until `rock` was added to `reads.kinds`, and nothing said why. Now a view of one is handed the records of its own kind that a relation it reads links to its record, in both directions, and only those; `reads.kinds` naming the kind still hands every record of it. A relation in `reads.edges` with an end the view is never handed is said, with the kind to add ("\"rock-page\" reads the relation \"foundIn\", from rock to place, and is handed no place, so no link of it reaches the view: add \"place\" to its manifest's reads.kinds."), among a headless run's problems (`graview view check`) and to the page host's `onProblem`. So is a relation to any kind (`to: "*"`) on a view of one that reads no other kind. `ownKindRelations`, `edgesReadWithoutTheirKinds` and `edgesReadWithoutTheirKindsSaid` are on `@graview/guest/host/views`.

The press check passes a control already in its state, only as one of a set. An "All" chip pressed while nothing is filtered changes nothing, rightly, and was refused as a control that does nothing. It now passes where another control beside it, or in its `role` group, says the same attribute's other state: `aria-pressed`, `aria-selected` on a tab, an option or a grid cell, or `aria-checked` on a checkable role. `aria-current` is written differently, on the one current link of a pager or a nav, so it counts on a link or a role that names a place (`link`, `tab`, `menuitem`, `treeitem`, `option`), beside a sibling of the same element and role with no `aria-current` or with `"false"`. A Save with a dead handler that says `aria-pressed="true"` alone still fails, as does `<button aria-current="page">Save</button>` beside any other button, an `aria-current` of `""` or `"undefined"`, and a state in a class alone.

A view may lay its cards in CSS columns and keep each whole in one. `columns` and its family were kept already; `break-inside`, `break-before`, `break-after`, their `page-break-*` forms, `orphans`, `widows` and `box-decoration-break` are now the open kit's too. The whole list a view's CSS is held to is `CSS_PROPERTIES` (with `CSS_FUNCTIONS` and `CSS_AT_RULES`) on `@graview/core/css`, which the `graview-view-drawing` skill now points to.

A brand lends its views web faces. A view's stylesheet still loads nothing, `@font-face` included. `brand.views.fonts` names a face and its one file (`{ "family": "Baloo 2", "src": "/graview/assets/<sha256>.woff2", "weight": "400 800" }`), and the view's host loads it into the page as a `FontFace`, only from where it already lets a view's images come from: a file the app holds, where the host says those are served (`asset`), or an `https:` address on an origin it lists (`images.origins`, read as an image's are). Anything else is said and not fetched. A view's sheet and the app's sheet for views then name it as any face. A face is in the page's document, so it may not be called what the page already draws in (a face every system has, Graview's own, one of the brand's own stacks), the host loads at most eight and says what it left out, and a face goes from the page when the brand stops lending it or the last view holding it is taken away. `graview check` and `set-brand` hold each face to the same rule (`brand-views-font`), `set-brand` says "Views may draw in Baloo 2.", and the diff says the same. `viewFontProblem`, `viewFontSource` and `brandFamilies` are on `@graview/core/css`.

The app's theme wins. The brand's `views.css` was drawn before each view's own sheet, both unlayered, so any rule a view wrote beat it and a design system could not hold. Every sheet in a view's region is now in a cascade layer of the host's: `graview-motion`, `graview-region`, `graview-view`, `graview-theme`, in that order. Where the theme and a view style the same element the theme's rule wins whatever the view's specificity. A view's `!important` and a `style` attribute on the element still go past it. **This can change how views look: a theme reset such as `*{margin:0}` now overrides every view's own margins, so an existing `brand.views.css` should be read again before this release.** Inheritance is not the cascade: a theme's font on an ancestor yields to a view's on its own element. Neither sheet can write `@layer`. The wrapper trusts no judge: it reads a sheet again before holding it, and draws nothing of one that is not whole rules (`readsAsWholeRules`). A headless run's `css` is drawn in the same layers, so a picture of the view is dressed as the page dresses it. `set-brand` now says "Every view is drawn with the app's own stylesheet, whose rules win over its own."

The root and the ring hold against a view's rules. With the region's rules in a layer, a view's plain `div{display:grid}` and `*{opacity:1}` could reach its root, so the root's `display: flow-root` and a fade's `opacity: 0` are `!important` now. The ring stands against `outline: none !important` in a sheet, and now in a `style` attribute too, where `!important` is left out on `outline*` and `all`, and against a transition that would hold it at its starting value. `--graview-focus-color` is refused: the ring is drawn in the app's accent, which the brand is judged on. `--graview-focus-width` (never under 2px) and `--graview-focus-offset` stay a view's. A view can still hide a control itself, or push the ring out of sight with a large offset.

Tests: `a-view-of-one-reads-its-own-kind-across-a-relation-back-to-it`, `a-press-on-a-control-already-in-its-state-passes-the-check`, `a-view-lays-its-cards-in-css-columns`, `a-view-draws-in-a-face-its-app-lends-it`, `the-apps-theme-wins-over-a-views-own-rule` and `a-views-sheet-stays-in-its-layer` (guest), and `a-brand-lends-its-views-faces-it-declares` (core). guest-sandbox's brand and presses transports prove in a real browser the theme winning, "Rock Face" and "Baloo 2" loaded and drawn and gone with the brand, an "All" chip passing and a dead Save failing the press check run in the page's own worker, cards kept whole in three columns, no request leaving for any sheet in `scripts/fixtures/sheets-that-try-to-leave-their-layer.mjs` while a control of the same text unjudged does ask, and the root and the ring holding.

A hosted page's first load grows by 0.2 KB more up front, for the shape of `brand.views.fonts` in the document schema (`scripts/budget-raises/view-authoring-friction-hosted-page.json`). Every face grows by 13.0 KB (5.0 KB gzipped), the guest host drawing a worker view on the open kit by 7.5 KB (3.1 KB gzipped), registering one by 1.4 KB (0.4 KB gzipped), and the embed with the studio handed in by 4.5 KB (1.9 KB gzipped), each under a raise of its budget.

Compatibility: ops and primitives — unchanged. Stored formats — unchanged. The wire — unchanged. The declaration and check finding codes — additive: `brand.views.fonts`, and the finding `brand-views-font`. Derived tool names and input schemas — `set-brand`'s `views` takes `fonts`. Changed: a brand's `views.css` now wins over a view's own rule on the same element, where the view's used to win; a view of one that reads a relation from its kind to its kind is handed the records it links to; `--graview-focus-color` in a view's sheet or the app's is refused.

What Graview Cloud does: read each app's `brand.views.css`, since it now wins over its views' own rules. `propose_view` and `get_problems` may now show a view's unreachable relation among its problems. A page that lends faces from an `https:` origin needs that origin in its `font-src` and in the view's `images.origins`; one that lends a file the app holds needs `font-src` to allow where `/graview/assets/` is served.
