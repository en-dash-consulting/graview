A document an older build wrote compiles again (FR-134). 0.1.16's American spelling pass renamed a setting's `honored` (was `honoured`) in the document as well as in the declaration, and its notes said the document format was unchanged. That was wrong. A document carries the app's settings as the declaration says them, so every document `toDocument` wrote before 0.1.16 with settings in it stopped compiling, each setting refused as `setting-not-honorable`: "Nothing knows how to apply "undefined"". Graview Cloud found it on a document exported under 0.1.10. A compiled app 0.1.15 made of such a document (FR-123) was built without complaint and drew settings that did nothing. Now every reader takes the old name as the new: `readDocument`, `compileDocument` and `compileDocumentWithoutCheck`, `appFrom` and `appFromOrCompile`, `diffDocuments` and `editDocument`. A document that says both keeps `honored`, and the document handed is never changed. `toDocument`, `compiled.document` and an edit write `honored`, so the next save writes the new name, and a stored document need not be rewritten to keep working. `appFromOrCompile` builds the compiled app it is handed when the document beside it differs only by such a key, rather than compiling again in the page. The renamed keys are one list, `RESPELLED`, read before any format upgrade step. `respellDocument` gives a host the document as this build reads it and the paths it respelled; `upgradeDocument` says them as `respelled`. The audit of 0.1.16 found no other renamed key a document, a compiled app, an op, a stored format or a wire message carries. A brand's connector kit `color` (was `colour`) and a rule's `judgment` (was `judgement`) are renamed in the TypeScript declaration only: the document carries no kit, and a rule in the document says `require`, `when` and `says`. Two fixtures were made by the older builds themselves from npm: a declaration with the reader settings as `@graview/core@0.1.10`'s `toDocument` exported it, and that document as `@graview/core@0.1.15` compiled and serialized it. A test compiles them on this build, checked, saves them back and builds the compiled app, and every document named for an older version among the fixtures must compile. The 0.1.10 document is a conformance fixture too, `document:shortlist-0.1.10`, so `conformance()` says so when a build stops compiling it. Another test records every key path a document has been able to carry and fails when one is no longer read under either name, so the next rename is caught before it ships. docs/stability.md says the rule and how 0.1.16 broke it. Reading the old names costs Cloud's hosted page about 0.8 KB up front: 566.3 KB of its 567 compiling, and 522.6 KB of 523 handed a compiled app.

Compatibility: additive, and a fix to the document format. `graview-document@1` reads a setting's `honored` under its old name again (was `honoured`), as every build before 0.1.16 wrote it, and writes `honored`, which a build before 0.1.16 reads as a setting it cannot apply. A host that keeps documents for builds older than 0.1.16 should keep writing them with that build. `@graview/core/document` gains `RESPELLED`, `respellDocument` and the `Respelling` and `Respelled` types, and `Upgraded` gains an optional `respelled`. What 0.1.16 renamed outright stays renamed, with no alias, as its notes said: the exports `normalize`, `summarize`, `humanizeField`, `colorsIn`, `connectorHueColor`, `humanize` and `honorSetting`; `SettingDeclaration.honored`, `brand.kit.connectors.*.color` and an invariant's `judgment` in TypeScript; the check finding codes `kit-color-unreadable` (was `kit-colour-unreadable`) and `setting-not-honorable` (was `setting-not-honourable`); and the CSS custom property `--graview-center-y` (was `--graview-centre-y`). A host that matches the two codes by name matches the new ones. Ops, stored formats, the compiled-app format, wire messages and tool names and schemas are unchanged. `capabilities().shipped` gains FR-134.
