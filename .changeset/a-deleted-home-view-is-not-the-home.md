A home view the host lists as deleted is no longer the home, and a view that falls back says why (Roadmap f-deleted-view-still-public, r-visitor-sees-lens-not-view). The home's own view had no name, so `tidyViews` — the registry as the host's kept views leave it — could take a deleted view off every list and every place but not off the home: a page handed the deleted view among the views it keeps drew it, to a signed-out visitor as to anyone. A home view is now registered with the name of the view that draws it (`registry.home(view, { name })`, which `registerWorkerView` passes; a draft passes none), the registry keeps every home view given in order (`homes()`, each a `HomeRegistration`), `layerViews` carries them with their names, and the tidied registry's `homeView()` is the last one that is not deleted, or the derived home where every one is. Hidden is a word for the lists, so a hidden home view is still the home. And a worker view that cannot be drawn — its code refused (as a code address that needs a signed-in session answers a visitor), a manifest the app no longer matches, a view past its limits — is still drawn as the kind's own face, now inside an element that draws nothing of its own (`display: contents`) and names the view and the reason: `data-worker-view-fell-back="<name>"` and `data-worker-view-failed="<reason>"`, on a place and on the home. Nothing in the framework chooses a view by who is looking: the embed's tests now hold that the owner, a visitor with no roles and a page that names nobody are drawn the same view at the home and at a titled place, and none of them the home view the host lists as deleted; react's, that a deleted home view falls back to the one given before it and to the derived home; guest's, that a view whose code was refused names itself and `source` around the face drawn in its place. The pages face alone carries 132 B more minified (65 B gzipped), and the guest host registering a worker view 291 B (72 B), each under a raise (`scripts/budget-raises/a-deleted-home-view-is-not-the-home-*.json`).

Compatibility: the five surfaces — unchanged. The JavaScript API — additive: `ViewRegistry.home`'s second argument, `ViewRegistry.homes` and `HomeRegistration` on `@graview/core`; a failed view's fallback is wrapped in one more element, which lays nothing out. What Graview Cloud does: hands a visitor's page the same `views` and `keptViews` it hands the owner's — the framework then draws them the same — and serves each view's code to a visitor (a view whose code is refused falls back with `data-worker-view-failed="source"`).
