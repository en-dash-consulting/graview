A drop on a worker view allows the one change it was made for, and nothing the view's code picks (FR-193, FR-92). Where some members may not see some records, an act from a view's own code applied when it carried a dropped file and every other argument was a dropped file, any record the view was shown, a record the same change made, or a value the app declares. The host never forgot a file it handed in a drop, so after one drop the view's code could keep sending acts with the same file for as long as it was mounted, up to a hundred calls a message, choosing for each which shown day or which declared value went in it — and a run of choices can spell what only this viewer may see: a family member's view put five moments on days that spelled, in base 3, a code in a vault a friend may not read, and the friend read it back from the days. Now the drop is bound to its gesture: the host keeps the record each drop was bound to (its `data-drop-connect`, or the `data-record` the target was drawn in, one the view was shown), an act under the drop's exception takes that record and no other, takes no value the view chose, and spends every dropped file it carries, so the host hands none of them to an act again; one file in several calls of one change is refused. A drop the view does not hear is made into records by the host as before. `CodeActContext.dropped` answers the drop (`DropGrant`, its `target`) rather than a yes, `judgeCodeAct` says what it `spent`, and the drop's `handed` hook is given the drop with the file. `a-drop-allows-only-the-change-it-was-made-for` holds it: the dropped files become moments on the day they were dropped on, from the view's own act, as one change; a moment on another day the view was shown is refused `press-only`; a second act with a file is refused, and so is one file in five calls of a change; words of the view's own beside the files are refused. With the field-sight check of `sightIsTotal`, the guest host registering a worker view carries 280 bytes more (92 gzipped), and drawing one on the open kit 533 (188), under raises of their own (`scripts/budget-raises/sight-side-channels-guest-*.json`).

Compatibility: ops and primitives, stored formats, the wire, the declaration and check finding codes, derived tool names and input schemas — unchanged. A view that handles its own drop where sight is not total puts each file in one act on the record the drop was bound to; one that passed a declared value or another shown record beside the files now has its act refused `press-only`, and asks for a press for it.
