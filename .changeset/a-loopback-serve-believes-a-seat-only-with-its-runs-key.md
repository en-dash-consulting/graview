A loopback `graview serve` believes a seat only from a request carrying its run's key. It kept a page on another origin out, and a name rebound to 127.0.0.1, but another account on this machine, or any program that is no browser, sends no `Origin` at all, and it was believed as any seat but the system's: it read the whole store, records the policy hides included, and wrote to it as any member. Now each run of `graview serve` on loopback mints a key (32 random bytes, `mintServeKey` in `@graview/ship/cli`) and says it only in its terminal, as the address to use (`address: http://localhost:5196/?graview_key=<key>`). A request is believed only when it carries the key: in `x-graview-key` from a program, in the `graview_key` query parameter on a page's WebSocket (which cannot set a header) or a page's leave beacon, or in the cookie a browser is given for opening the printed address (`HttpOnly`, `SameSite=Strict`, a value made from the key rather than the key, and the address tidied by a 303), each compared in constant time (`sameKey` and `tradeKey`, shared with the dev server's doors). Without it every route but health answers 401 with where the key is, and so does the live wire's upgrade; a browser's preflight passes, and the key is never written into an answer, nor handed past the door to a route or a host's `answer`. A new run is a new key. `serveStore({ key })` turns it on for any host; `SERVE_KEY` names the header, parameter and cookie, and `servedAddress` takes a printed address apart into where the store is and its key, from the main, browser and runtime entries. `openRemote`, `remoteFriction`, `remoteSubscriptions` and `remoteViews` take the printed address whole and send its key as the header, so `graview mcp --remote-url` and `graview apply --remote-url` do too, and say where they act without the key; the rota page's `?server=` takes the same address. `a-loopback-serve-believes-a-seat-only-with-its-runs-key.test.ts` holds that a program with no Origin and no key claiming a member's seat is refused, that the header, the query and the traded cookie are believed, that the live wire keeps to the same rule, that `openRemote` opens live from the printed address, and that the key appears in no answer. The served and desk harnesses read the key from the address `graview serve` prints and hand the rota page that address, as a person would, and the served harness says a seat without the key, or with another run's, is refused. The graview-ship and graview-agent-seat skills say how.

A hosted page carries 0.5 KB more up front, minified, with or without a compiled app handed it (498 and 500 bytes, 178 gzipped): `openRemote` taking the printed address apart and carrying its key. `graview preview` keeps its page to its own origin as before and asks for no key yet.

Compatibility: the wire — a loopback `graview serve` answers 401 on every route but health, and on the live wire, to a request without its run's key, and its CORS answer allows the `x-graview-key` header; `graview serve --trust-seat-headers` behind a trusted network, and a host with its own `seatOf`, are unchanged. Ops and primitives, stored formats, the declaration and check finding codes, derived tool names and input schemas — unchanged.
