A live client lists records in the server's order whatever came in between. `ship`'s live-wire test, three clients making random renames, notes, adds and undos side by side, failed about three runs in five on a laptop (CI happened to pass it): a client held the same records with the same fields and the same log as the server, but two records listed the other way round. A store puts its graph back to a snapshot it held whenever a call is refused — a rename of a record a pending undo took out, or a pending batch that no longer applies over what the server sent — and that put-back ranked every record and link afresh and forgot where each one it had taken out stood. A rollback of the pending removal then put the record back at the end rather than where it stood, and once the server refused the removal the client's list and its collaborators' disagreed. A graph put back to a snapshot it held now keeps each record's and link's place, and what it had taken out keeps its own for a rollback; a graph loaded from elsewhere is ordered afresh, as before. `core`'s test removes a record, has a call refused, and rolls the removal back; and rebases a removal under a pending batch that no longer applies, then drops the removal: both put the record and its links back where they stood, as the server holds them. The live-wire test passes 20 runs in 20. A hosted page carries 0.3 KB more up front (291 bytes, about 71 gzipped; the compiled page the same, 85 gzipped), under a raise of each budget by that (`scripts/budget-raises/a-graph-put-back-keeps-where-things-stood-*.json`), and the scene face's limit before it draws is 1001 KB.

Compatibility: ops and primitives, stored formats, the wire, the declaration and check finding codes, derived tool names and input schemas, the JavaScript API, the theme and the embed — unchanged. A client's graph now lists records in the server's order after a refused call where it could list them in another; the log was already the same.
