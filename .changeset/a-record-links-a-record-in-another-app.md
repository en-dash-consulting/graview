A relation can go to a kind in another app, and the linked record is read there as whoever is looking (FR-171, the full relation). 0.1.29 named another app; this names a record in it. A relation's `to` may be `"@<app address>/<kind>"` — `"forHouse": { "to": ["@nick/house/house"], "cardinality": "one" }` — and `linkedRecordField("@nick/house/house")` says the same in a declaration, which `toDocument` writes back as the relation. Linking picks a record there and never touches the other app: the record that links keeps which one under the relation's name, as `"house:h1"` (or a list), so its derived edit sets it, undoes it, logs it and keeps it from a seat a sight keeps it from like any value. `graview check` says in sentences what such a relation cannot be — `linked-mixed`, `linked-apps`, `linked-target`, `linked-inverse`, `linked-append-only`, `act-linked`, `rule-linked` — with the checker, so a page that compiles without it carries none of their words. The host reads the far side beside `resolveApp`: `linkedRecords` on `mount`, `<Embed>`, `GraviewProvider` and the routed face answers `resolve(ref, viewer)` with the record's label, describe line, card and the fields that viewer may see, `{ denied: true }` or `null`, `find(search, viewer)` with the records that viewer may link, and `open(ref, viewer)`, optional, the seam a press on a linked record opens it through. The record's page and the scene's record panel draw it with its own card from its home app, and a document card's `{ "field": "forHouse" }` names it; a viewer the host refuses sees "linked record (no access)" and nothing of it. "Change" beside it, a form and the scene's ask pick another from what the host lists. The rule language walks it by name, `forHouse.listPrice`, in a computed field, a block or a rule, as the viewer: a far record it cannot read reads as nothing and is said — a computed value says why it has none, a rule that would not hold without it cannot be judged — and never thrown; the page reads again as each answer arrives (`store.reread()`). When the far value changes, the host calls `recordLinkedChange(store, { ref, fields, app })` and the reading app's history keeps an op authored by the other app on each record that links it — "Buy it outright: the linked record changed in House — list price" — naming what changed and none of its values. `describe_app` lists each relation under "Linked from other apps" with how to link one, the derived edit's tool says its argument is a record of that app as `"<kind>:<id>"`, and a seat finds one with `find_linked`, listed only for an app with such a relation. `@graview/core/linked` holds `linkedRecordsOver`, the host over stores held in memory, read through each far store's `seenBy(viewer)`, which the tests read two compiled documents through and a host holding both apps can use as it is; `graview-linked-records` is the skill that teaches it. A hosted page's first load is 5 107 bytes larger (550 088 over the vendors document, 544 981 on main), 4 648 handed a compiled app, both under their budgets; what draws a linked record is a chunk fetched with the first one drawn, and the embed's budgets are raised by files of their own: the pages face 4 585 / 1 704 bytes minified / gzipped, every face 20 162 / 7 423, the studio handed in 13 618 / 4 936.

Compatibility: additive. The document format gains a relation target `"@<app address>/<kind>"` in `kinds.<kind>.edges.<name>.to` (`document.schema.json`'s `edges.to` items match a kind name or that target), its value kept on the linking record as `"<kind>:<id>"` or a list of them, and `graview-compiled@1` carries it; a build that predates it refuses such a target by path. The check gains `linked-mixed`, `linked-target`, `linked-apps`, `linked-inverse`, `linked-append-only`, `act-linked` and `rule-linked`. `mount`, `<Embed>`, `GraviewProvider` and the routed face's context gain an optional `linkedRecords: { resolve(ref: { address, kind, id }, viewer): Promise<{ address, kind, id, label, describe?, card?, fields, href?, app? } | { denied: true } | null>; find({ address, kinds, query, limit }, viewer): Promise<LinkedRecord[] | { denied: true }>; open?(ref, viewer): void }`. Ops and primitives are unchanged: a far change is an ordinary op appended with author `{ kind: "system", id: "app:<address>", name }`, `via: "app:<address>"`, the linking records in `reads` and no primitives. `ReadableField` gains `linked`, a form gains the control `linked`, a document card's resolved field block gains `linked`, and the derived `edit-<kind>` of an app with such a relation describes its argument with `"x-graview-linked"`; an app with none has the same tools as before. What a host does: read `capabilities().shipped` for FR-171 before writing such a relation, pass `linkedRecords` to have a linked record drawn and walked, and call `recordLinkedChange` when a far value changes.
