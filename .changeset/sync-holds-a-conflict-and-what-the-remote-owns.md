The sync engine decides a conflict as it is told, refuses what the remote owns, and is its own entry. A product that projects another system into Graview and syncs back (n-dx's face, over rex) found the engine pushed our value for a field in the same pass it reported that field as a conflict, so the remote was overwritten before anyone could choose; it pre-empted every run by hand. `SyncEngine` now takes `conflicts: "report" | "theirs" | "ours"`. `report`, the default, holds a field both sides changed and sends neither value until `resolve` says which stands, and a later pass that hears nothing new still reports it; `theirs` lands the remote's value through `applyInbound`, authored by the system like any inbound change; `ours` sends ours in the same pass. The report's new `resolved` says each conflict the policy settled and which side it took, and `conflicts` is every one still held.

A mapping's resource may be `readonly`, with a `because` sentence: inbound changes land, nothing is sent, and once `sync.guard()` holds the store, an act that would write a record of it is refused with that sentence as a `PermissionDeniedError` (`sync.admit` is the same judgment as an `ApplyOptions.admit`; `sync.refuses(kind)` says it before an act is offered). A resource's `version` names our field that holds the remote's version, and every record that carries one is linked at it when the engine is made, so a projected graph's first run sends nothing. A local delete the remote refuses, or of a record the remote owns, is refused once with its reason and the link let go, where it was refused again on every pass. A field the mapping only sends (`ours`) is agreed after a push, where it was sent again every pass.

A remote that speaks MCP is `mcpRemote({ name, call, pull, push })`, one write at a time, each refused alone. `call` is `mcpClient({ url, allow, headers })`, which opens a streamable-HTTP session, reads a JSON or event-stream answer, opens another session once when the server forgot it, and refuses a tool not in `allow` before sending it; or, in a page, `doorClient()`, posting to `mcpDoor({ call, allow })` on the server, which holds the token and passes only a POST of `application/json` from its own origin (`sameOrigin`) naming an allowed tool (`allowTools`), saying which it refused. None imports a `node:` builtin.

A store attributes what its reader does: `new Store({ principal })`, or `openStore({ storeOptions: { principal } })`, is the author of every apply and undo that names none, where it was always a person with no name. `rememberedPrincipal()` on `@graview/ship` and `@graview/ship/browser` reads the name a page keeps under `graview:principal` (`PRINCIPAL_KEY`), "reader" when it keeps none or storage is locked away. The hosted page measures 593_548 bytes up front, 59 fewer than before: the store's constructor builds its graph from one `validate` it already held.

Compatibility: ops, stored formats, wire messages, the document format, the compiled format, check finding codes and tool names and schemas are unchanged. Changed: the sync engine, its mappings, its conflict invariant and the Google Calendar transport left `@graview/core` for `@graview/core/sync` (`SyncEngine`, `googleCalendar`, `googleCalendarMapping`, `syncConflictInvariant`, `SYNC_CONFLICTS`, `EMPTY_SYNC_STATE`, `systemAuthor` and their types); a conflict is held and not sent unless `conflicts` says otherwise; `SyncReport.conflicts` is every conflict held, and `SyncState` may carry `conflicts`; `resolve(conflict, "ours")` re-bases on their value. New: `conflicts`, `resolved`, `guard`, `admit` and `refuses` on the engine; `readonly`, `because`, `version` and `remoteId` on a `ResourceMapping`; `mcpClient`, `mcpDoor`, `doorClient`, `mcpRemote`, `allowTools` and `sameOrigin` on `@graview/core/sync`; `principal` on `StoreOptions`; `rememberedPrincipal` and `PRINCIPAL_KEY` on `@graview/ship`. What Graview Cloud changes: nothing.
