A workflow run says what its model steps spent and which workflows started it, a chain of workflows waking each other stops at a limit, the Scene reads a run's counts, and a classify step labels what no option clears and sets what it is sure of, Roadmap feature:f-workflow-runs-say-more (request:workflow-run-said-takes-counts, request:workflow-run-says-model-spend, request:classify-step-reports-usage, request:workflow-chains-with-a-depth-limit and request:classify-step-otherwise-and-apply-at, from Graview Cloud after it took 0.1.63's workflows). A host had to send record ids, or filler arrays of the right length, for the Scene to say "made 3". It had to wrap `complete` and `decide` to meter a run. Two workflows whose changes started each other ran without end. And a record no option fit was left unlabeled, with every label asked of a person however sure the model was.

Now the Scene's `RunSaid` (`workflowRuns`, `lastRunWords`) takes each of `made`, `changed`, `archived` and `suggested` as the ids or a count (`RunCount`, `runCount` on `@graview/core/scene`), and the words are the same either way. A `WorkflowRun` carries `spent`: calls, input and output tokens and cost, by step (`steps: { step, calls, inputTokens, outputTokens, costUsd?, model? }[]`) and in all. Each step records its own spend through `StepContext.spent`. The agent step records its reply's `usage`, and a call the model failed to answer counts as a call with no tokens. The classify step records the requests it sent through `decide` and the tokens its answers said, and a label answered from the cache spends nothing. A dry run's calls are counted too. The generate step asks no model and records nothing.

`triggeredBy` says which workflow's run made the ops that fired a trigger (`by: { workflow, run? }`, read from `lineage.run` or the `workflow:<name>` author; `workflowOrigin(op)` on `@graview/core/workflows`). A run started with `trigger.by` carries `chain`: the workflows behind it, the first first, read from the starting run in the host's log. Its length is the run's depth. A run deeper than `runWorkflow`'s `chainLimit` (`MOST_CHAIN`, 3, when unsaid) is held, dry, and says so in words: "“Answer a ping” was started by a chain of 4 workflow runs, each started by the one before (“Answer a ping” → “Answer a pong” → …), past the limit of 3: it did not run." `two-workflows-that-wake-each-other-stop-at-the-chain-limit.test.ts` runs two workflows that do exactly that.

A `classify` step takes `"otherwise": "<option>"`, the label a record no option clears is given (the model chose none and no floor rule holds), and the run says how many it labeled so. It also takes `"applyAt": { "<option>": 0.85 }`: a judgment at or above that is set without asking (`StepChange.apply`, `classifyApplies`), and one below it waits as the step says. An option in `confirm` is asked whatever `applyAt` says. `graview check` holds both to the codes the step already had: an option the field lacks is `workflow-classify-option-unknown`, and an `applyAt` past 0 to 1 is `workflow-classify-threshold-invalid`. The step's line says both ("…, else needs-look; sets spam at 85% sure without asking"). The graview-workflows skill says how, and docs/stability.md says what a host reads off a run.

Compatibility: ops and primitives — unchanged: a run's ops carry the `lineage.run` they did. Stored formats — unchanged in the graph; the runs a host keeps gain `spent` and `chain`, and a run kept before them reads as a chain of none. The wire — unchanged. The declaration and check finding codes — a classify step gains the optional keys `otherwise` and `applyAt`, which a build before this one refuses by path; no code is new, and no declaration that passed is refused. Derived tool names and input schemas — unchanged; `run_workflow` answers as it did. `WorkflowRun` gains `spent` and `chain`, `StepContext` gains `spent`, `StepChange` the optional `apply`, `RunWorkflowOptions` the optional `chainLimit`, a `made` or `changed` trigger the optional `by`, and `FiredTrigger` the optional `by`.

What Graview Cloud does: hands the Scene its counts as numbers and drops the filler arrays, meters each run from `run.spent` rather than wrapping `complete` and `decide`, passes each `FiredTrigger.by` into the run it starts (its `WorkflowLog` keeping `chain` beside the rest), and offers a classify step's `otherwise` and `applyAt` in the declarations it writes.
