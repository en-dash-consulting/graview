A view takes files dropped on it (FR-193). Roadmap f-views-take-a-drop: Graview Cloud's family weekend wanted photographs and a phone's video dragged from Finder onto a day's card on its journey home view to become moments on that day; a worker view had no way to receive a file, and no act argument could carry one. A view now marks the element — `<section data-drop="moment" data-drop-connect="takenOn:day:saturday">` — and its manifest says which fields files become: `accepts: [{ kind: "moment", field: "photo" }, { kind: "moment", field: "clip" }]`, each a kind and its image, video or file field (`checkManifest` refuses a kind the app lacks, a field that holds no file, and a kind no act makes with that field). The host owns the rest. It offers the element as a drop target only where this seat may make that kind and link it, and the host's files take what its fields hold (`data-graview-drop`, said to assistive technology); while files are dragged over it the host draws it with its own outline and says what dropping there does, in a status of its own; on a coarse pointer the same element is a tap that opens the picker, asking for what the fields take (`image/*,video/*`), and Enter or Space on it does the same anywhere. Each file is held to the field its type fits (a picture to `photo`, a video to `clip`) and to the host's `kinds` and `maxBytes`, stored through the host's `files.upload`, and what was refused is said one sentence a file while the rest go on. A view that does not hear `drop` gets, per file, a record of the kind with its file on its field, linked as `data-drop-connect` says — by an act on the dropped-on record that makes one linked where the app has it, else the act that makes the kind and the derived "Set the day" — all in one change that one undo takes back, said "Added 4 moments to Saturday." A view that hears it (`graview.on("drop", "[data-drop]", (event) => …)`) is told once, with `event.files` as the host stored them — `{ href, name, type, bytes, width, height, poster, duration, at, field }`, never their bytes — and `event.refused`. `graview.act(name, [args, …])` runs several of one act as one change, and an act's argument takes a file only as the host handed it, in a drop or on a record the view was shown, going as the host kept it; any other `href` is refused. Where sight is not total, an act from a view's code still applies only from a press, except one that carries a drop's files and nothing the view could have read. `applyAll` takes `{ $made: n }` in an argument, the record call `n` of the same change made (`made(n)` from `@graview/core`), and judges that call once the record is there to name. A headless run (`graview view check`, `runWorkerViewHeadless`) says a `data-drop` of a kind or `data-drop-field` the manifest does not accept, and a `data-drop-connect` that is not `<relation>:<record id>` or names a record the view was not shown. A file field's editor on a host whose files take nothing (`maxBytes` 0) offers no picker and says the host takes no files, never "up to 0 bytes"; an empty video field on a record's page is drawn as its editor where the host takes `video/*`, as it already was, now held by a test. The graview-view-drawing skill teaches the drop, and every event a view hears as `{ type, target, element }` with what it carries: `value` and `checked`, `key`, `pressed`, `files` and `refused`. The guest-sandbox drop harness proves it in Chromium, WebKit and Firefox. A hosted page's first load carries 0.7 KB more (0.3 KB gzipped), the store's `{ $made: n }`; the drop itself is fetched only with a view that draws a drop target. `capabilities().shipped` gains FR-193.

Compatibility: ops and stored formats are unchanged; an op keeps the record id a `{ $made: n }` was read as. The declaration: a worker view's manifest takes `accepts`. The wire: a worker view's runtime sends `{ type: "hears", events }` the first time its `graview.on` listens for each event, an act request's `args` may be a list of argument objects (1 to 100) for several of one act as one change, and the host sends a `dom-event` whose `event` is `drop`, carrying `files` and `refused`; a view that asks for none of it is sent nothing new. Derived tools are unchanged, and `capabilities().shipped` lists FR-193. What Graview Cloud does: mount views as it does — the page's `files` (`filesAt` under the app's base) is what a drop is stored through, so the files route's upload is the whole seam; let `propose_view` take `accepts` in a view's manifest; and teach `data-drop`, `data-drop-connect`, `accepts` and `graview.act(name, [args, …])` in its views guide.
