A view's pictures are drawn lazily and handed at the size each use needs (Roadmap f-view-pictures-load-lazily-and-small). A home that drew sixty record photos could not say which to draw first, since an `<img>` with `loading` was refused ("<img> does not take loading"), and each photo came at the width of its hero even where it was drawn as a chip. An `<img>` in a worker view now takes `loading` (`"lazy"` or `"eager"`) and `fetchpriority` (`"high"`, `"low"` or `"auto"`); any other value is not drawn, and the host says the ones it takes: `Not drawn: the value of loading is not one the open kit takes. An <img> loads "lazy" or "eager".` What they order is the page's own work on a picture the view was handed — when an `<img>` off the screen is decoded and drawn, and which comes first — not the host's fetching: the host still fetches and makes smaller every picture a view is handed, when it is handed, as before. What a view is handed is still bounded by its kinds, `records`, `most` and its budget.

A view may ask for two sizes: `pictures: { width: 1200, thumb: 240 }`. Each picture handed an address then comes with `thumb` beside `src` — a second address the host made from `src`'s bytes at the thumb's width, so the picture as fetched is decoded once — and a chip draws `thumb` while a hero draws `src`. A thumb is a still: an animated picture handed as it is keeps its animation in `src` alone. Where a thumb would be no smaller than `src` (a picture no wider than the thumb, or one the page could not make smaller) none is handed, so a frame is never posted the same `data:` image twice, and a view draws `thumb || src`. Both sizes are reckoned against the view's picture budget before either is made, each at the width it is made at, erring high: a picture no wider than the thumb is reckoned once, one whose record says no width at its bytes twice. A headless run hands the stand-in for both. It is the same path for a frame (`pictures` on its host's options), and `records` and `most` work beside it.

`checkManifest` refuses a thumb that is not a whole number of pixels from 16 to 4096 narrower than the width: `The view's pictures thumb is a whole number of pixels from 16 to 4096, narrower than its width (1,200 by default): the size it draws a picture small at (view-pictures-thumb).` A frame's host, which no manifest check reads, is told the same once (through `onLeft`, else the console) and makes no thumb. As with `records` and `most`, a string or a list under `thumb` still names a kind called `thumb` and its fields. The `graview-view-drawing` and `graview-worker-view` skills say both.

The unit test `a view's pictures load lazily and at the size each use needs` (guest) holds it.

Compatibility: the declaration and check finding codes — a worker view's manifest takes `pictures.thumb`, refused with the new finding code `view-pictures-thumb`; every manifest that passed still passes. The wire — a `GuestFile` may carry `thumb`, only for a guest that asked for it. Ops and primitives — unchanged. Stored formats — unchanged. Derived tool names and input schemas — unchanged.
