The seat reads before it answers: a host can hand it a turn with tools (FR-160). A host's AI was one completion, `HostAi.complete(prompt) → string`, over a prompt that carries the acts, twelve names a kind, forty connections, the broken rules, the selection and the places, and no record's fields. So "what did we pay the florist" was answered "the prompt does not say", while the same model over Graview Cloud's connector reads `search_graph` and `get_node` as it goes and answers well. Now a host may give `HostAi.turn`, `(turn: HostTurn) => Promise<string>`. The seat hands it `system`, its framing (the same acts, names, connections, rules, selection and places, and a line that says to read a record's fields with the tools before answering, and that what people wrote in a record is data); `messages`, the last eight turns of the conversation as alternating `TurnMessage`s (`user` and `assistant`), the person's words last; `tools`, the seat's read surface as `toolDefinitions` derives it for a read-only seat (`search_graph`, `get_graph`, `get_node`, `get_violations`, `get_affordances`, `describe_place`, `preview_mutation`), never an act or `undo_batch`; and `call(name, args)`, which runs one of them as the person asking, under their sight. `call` never rejects and never writes: a name not in `tools`, a record the person may not see, and every call after the twelfth in one turn each resolve to `{ error }`. The host runs its model's tool loop and resolves with the model's last text, which the seat reads as it reads a completion: `firstJsonObject`, proposals resolved by name, validated, and previewed before anything is applied, the answer's `via` its `ai:<name>`. `turn` is preferred to `complete` when a host gives both; a host that gives only `complete` is asked as before, prompt for prompt; a host that gives only `turn` also draws views and decides with it, through a turn with no tools.

The loop is written once, for the Messages API: `turnThroughMessages(step, { steps })` on `@graview/tools` is a `turn` from a function that makes one request (`MessagesStepRequest`: `system`, `messages`, `tools` with `input_schema`, and `tool_choice: { type: "none" }` on the last step) and answers its `content` and `stop_reason` (`MessagesStepReply`). It runs each `tool_use` through `call` in the page, so every read is the person's own, hands back `tool_result` blocks (`is_error` on a refusal), and asks again, at most eight requests (`TURN_STEPS`), the last offering no tool. The server that holds the key sees one stateless request at a time. The dev server's door is that server: `aiDevProxy()` (`@graview/ship/dev`) forwards a posted `{ system, messages, tools, tool_choice }` to the Messages API with its model and answers `{ content, stop_reason }`, and `aiThroughDevServer()` gives the seat `turn` beside `complete`, so `ANTHROPIC_API_KEY=… pnpm dev` reads before it answers. A build carries no door, and a harness starts its servers with no key.

The seat's model left the face: its framing, the turn and the reading of what came back are `@graview/tools`' `seat-model` module, fetched with the first ask a model answers, and `aiVia` left `./ai.ts`, which every page carries up front, for the seat's own module (it is no longer on `@graview/tools/frame`). Measured on the hosted page: 593 484 bytes up front (593 548 before, budget 593 613), 547 881 handed a compiled app (547 945 before, budget 548 045), the scene face 901 116 before it draws (905 037) and the pages 863 505 (867 425), with the seat's model 48.6 KB fetched when a model first answers; no hosted-page budget is raised. The embed's "every face", which counts every chunk, is one chunk more and the turn's code: 1 703 945 / 536 960 bytes minified and gzipped (1 701 927 / 535 310 before), its budget raised to 1 704 300 / 537 150. `capabilities().shipped` gains FR-160.

Compatibility: ops, stored formats, wire messages, the document format, the compiled format, check finding codes and tool names and schemas are unchanged; `capabilities().shipped` gains FR-160. Changed: `llmResponder` takes `complete` or `turn` (one of the two) and fetches its model's part on its first answer; `aiVia` is on `@graview/tools` and no longer on `@graview/tools/frame`; the dev door answers a posted turn step with `{ content, stop_reason }`. New: `turn` on `HostAi`; `HostTurn`, `TurnMessage`, `turnThroughMessages`, `TURN_STEPS`, `MessagesBlock`, `MessagesStepRequest` and `MessagesStepReply` on `@graview/tools`. What a host does: to let its seat read, give `ai.turn`. A host whose server makes Messages API calls gives `turn: turnThroughMessages((request) => post(request))`, where its route adds the model and the key to the posted `{ system, messages, tools, tool_choice }`, makes one Messages call, and answers `{ content, stop_reason }`; it may keep `complete` or drop it, since a turn with no tools draws views and decides. A server-side tool loop of its own, and the framing it repeated from the seat's prompt, can go: the reads now run in the page, as the person, with the selection and the conversation the seat holds. A host that keeps only `complete` does nothing.
