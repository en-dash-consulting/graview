A worker view's draw budget fits the device, Roadmap f-view-budget-fits-device. The time a view had over one push of what it is shown (`pushMs`, 1 000 ms) and the page's own time drawing what it sent (`drawMs`, 100 ms of any second) were fixed numbers, so the slowest devices lost their views first: on a car's browser the home-screen views fell back to the app's own page as "took longer than 1,000 ms to draw" while the same views drew well inside a second on a laptop. The page now measures how long its first view's worker took to start — from `new Worker` to its runtime's ready, which is the device making a thread and parsing and running the view's runtime — once, keeps it (`device-pace.ts`; the second view on the page needs no measuring), and every view is given its base times that pace: 1 for a start of 60 ms or under, so a laptop keeps today's guard, rising to a tenth to a ceiling of 4 at 240 ms or more. The base is the host's own `pushMs` and `drawMs` where it gives them, else the defaults, so Graview Cloud's 3 000 / 300 scales the same way and never past four times; the message allowance, the node cap and the byte limits never scale, so a flood is a flood on any device; the headless runner's budget is the server's and stays fixed. The sentence a stopped view is given names the budget it was actually held to ("It took longer than 2,400 ms to draw what it was shown."), the mounted view says the page's `pace` once its worker is ready, and the page keeps whatever it shows — the drawing before, or nothing — until the view draws or that budget runs out: no fallback was drawn before a first draw and then swapped, and none is now. A start the network slowed (`worker: { url }` answered late) reads as a slow device too, which gives a view on a slow link a slow device's time and no more of anything else. The guest's tests hold it with a stand-in worker that says ready when told (`a-worker-views-draw-budget-fits-the-device`: pace 1 on a fast start, 4 at the ceiling, the host's base honored, the counts unscaled, the second view given the first one's pace), and `guest-sandbox --transport=limits` holds it in Chromium, WebKit and Firefox: the limits page is at one pace, measured once from its first worker's start — 1 on a laptop at rest, reported rather than fixed, since three harnesses side by side can make a first start slow — and stops its spinner as slow at that pace times 1,000 ms with the sentence naming it; and a page whose views come from a script the server holds 300 ms is at pace 4, where a view that draws in 300 ms draws, one whose listener takes 1 500 ms a push draws, the spinner is stopped at 4,000 ms with the sentence naming it, and the flood is stopped at the same 120 messages. Under `GRAVIEW_SLOW=4` the suite throttles each page's main thread as the nightly's runner is, and the limits page measures its first start slower (pace 2.1 on this laptop) and holds its spinner to that — the engine throttles no worker, so the throttled main thread is what a slow device looks like to the host. The guest README and `graview-worker-view` say the budget fits the device. The guest host drawing a worker view on the open kit is 0.4 KB larger (408 bytes minified, 154 gzipped: the pace kept and fitted, the draw budget reading its allowance at each batch, the view saying its pace), fetched only when a worker view first draws, and the guest host drawing a kit worker 30 bytes minified (the shared start measuring itself) — the raises in `scripts/budget-raises/a-worker-views-draw-budget-fits-the-device-*.json` say each entry's bytes; a page's first load is unchanged.

Compatibility: ops and primitives, stored formats, the wire, the declaration and check finding codes, and derived tool names and input schemas — unchanged. What Graview Cloud does: nothing; its 3 000 / 300 for people's pages (branch cloud/view-budget) is scaled by the page's pace as the defaults are, and it may drop that branch and take the adaptive default.
