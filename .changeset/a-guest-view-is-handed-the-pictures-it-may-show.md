A guest view is handed the pictures on the records it reads, as addresses the host made from the bytes (FR-175). A record keeps a file as a path on the host (FR-162's `FileValue`), which the host serves to the app's members with their credentials; a worker view and a frame run at an opaque origin, so a view of a job's photographs was handed paths it could not load, and learned the host's paths besides. A worker view whose manifest says `pictures: true`, or `pictures: { width: 400 }` (the widest it draws a picture, in CSS pixels; 1 200 by default), and a frame whose host passes `pictures` to `mountGuestView` or `guestView`, is now handed each file on a record as a `GuestFile` in the record's own field, never the path: `{ name, type, bytes, width?, height?, caption?, src?, left? }`. A picture (`image/*`, not SVG) carries `src`, which the host made from the bytes it fetched on its own origin as the reader (`credentials: "same-origin"`): a `blob:` URL of the page for a worker view (a `data:` image where the page's policy refuses `blob:` images), a `data:` image for a frame, as the brand's logo is (FR-127). It comes without `src` on the first push and the view is pushed again once the host has made it. A document, and an SVG, is its name, type and size alone, and is never fetched. Only files on records the guest is handed are fetched, so a file on a record the seat may not see is never asked for. A picture wider than the view draws one (`width` × the screen's pixel ratio, at most 2) is made smaller on a canvas, kept in its own type where the canvas writes it; one picture is at most `limits.pictureBytes` as handed (1 500 000 by default) and a view's pictures together at most `limits.picturesBytes` (12 000 000); a picture left out says why in `left`, naming the view — "The picture "porch.png" on "Porch repair" is left out: the view "Job photos" is handed at most 12,000,000 bytes of pictures, and the pictures before it took them." — and a worker view's console and `onProblem` hear it once. Pictures past the view's budget are not fetched. A frame that asks is answered once the pictures' host has arrived, and a worker view starts once it has; the pictures' host is a chunk of its own, fetched only for a guest that asks. `checkManifest` says what is wrong with a manifest's `pictures`. Headless (`graview view check`, `runWorkerViewHeadless`), a view that asks is handed each file without its path and without `src`. The graview-worker-view skill says in one line how a view shows a record's picture. `guest-sandbox --transport=pictures` draws a worker view of a crew's jobs as a member on one of them, in Chromium, WebKit and Firefox: the pictures are `blob:` URLs of the page made from bytes fetched once each with the reader's session, the step's byte for byte and the porch's, 1 600 pixels across, made 400; the PDF and the SVG are said by name, type and size; nothing the view drew names a path on the host; and the roof's photograph, on a job the member is not on, is never requested. A hosted page's first load is 391 bytes larger (587 597 bytes over the vendors document, 587 206 on main; 546 594 handed a compiled app, 546 203 on main), the frame's wait for the pictures' host; the guest host before a worker is drawn is 400 bytes more, registering a worker view 547 more, and a worker view on the open kit 5 353 more, the pictures' host itself, each raised by a file of its own in `scripts/budget-raises/`. `capabilities().shipped` gains FR-175.

Compatibility: ops, stored formats, the document format, the compiled format, check finding codes and tool names are unchanged. The guest protocol is additive and `GUEST_PROTOCOL` stays 1: no message is new, and a guest that does not ask for pictures is handed each file as the record keeps it, as before; one that asks is handed a `GuestFile` in that field instead. New: `GuestFile` from `@graview/guest` and `@graview/guest/host`; `WorkerViewManifest.pictures`, `MountGuestViewOptions.pictures`, `GuestViewOptions.pictures`; `GuestLimits.pictureBytes` and `GuestLimits.picturesBytes` (`GuestPictureLimits`), and `GuestPictures`, from `@graview/guest/host` and `/host/views`; `GuestHostOptions.hand`. `capabilities().shipped` gains FR-175. What Graview Cloud does: nothing to serve, since its files route already serves each file to the reader with their credentials on the page's own origin; a view it stores may say `pictures` in its manifest once `capabilities().shipped` includes FR-175, and a view's author draws `<img src="${photo.src}">` once `src` comes.
