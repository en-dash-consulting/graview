A record taken away while the history plays comes down on a slow machine too. Its building was kept for the sink's length counted from the render that found it gone, so where the render, the commit and the style a scrub sets off took most of that time — a CPU four times slower, as a runner's is — the building was taken away part way down, or before a frame showed it sinking (one-face's `aRemovedRecordComesDown`, under GRAVIEW_SLOW=4 on GitHub's runner). And a building going was drawn last among its village's blocks, so React moved its element, and an element moved loses the sink under way on it: it went flat in a frame. A building going now stays where it stood among the others (`inTheirPlaces`), and is taken away when its sink has played out, by the sink's own end once it is drawn flat (a rise that ends in the frame it is marked going is not its sink's end); a clock of twice the sink's length, started once the sink is on the page, is only for where none plays (less motion). `aRemovedRecordComesDown` now also asks that the building is seen part way down, not flat in a frame, and its verdict carries each building's frames when it fails. Nothing a host calls changes.
Compatibility: the look — a building going sinks where it stood, all the way down. The JavaScript API, ops and primitives, stored formats, the wire, the declaration and check finding codes, and derived tool names and input schemas — unchanged.
