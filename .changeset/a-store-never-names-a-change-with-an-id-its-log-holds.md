A store never names a new change with an id its log already holds (FR-204). Graview Cloud's fleet replay after 0.1.47 found three production apps whose logs named the same change twice (`op1186` at seq 1112 and 1113, `op253` at 253 and 254, `op493`–`op496` and `op503`): Cloud wakes a room by opening the store on the log up to its snapshot and taking the rest with `store.receive(tail)`, and while the constructor and `adopt` wound the op and batch counters past every id the log held, `receive` did not, so the next change was minted with an id the tail already held. Undoing one of such a pair undid both, a client's `receive` dropped the second as already known, and `importBundle` refused the backup. `rebase` did the same with the server's confirmed ops before it applied the pending ones again, and `append` with ids a host named. Now every path that takes ops counts past them: `receive` (applied or not), `rebase` before it mints the pending batches afresh, `append`, `adopt` and the constructor, through one `countPast`. `core`'s test opens a store on part of a log, receives the rest and mints a fresh id; receives into a store that already wrote; receives ops already applied; rebases over a server that moved on; adopts; reopens; and appends a host's `op7`, and every log it leaves holds each id once and each turn's ops together. A hosted page carries 0.1 KB more up front (85 bytes, about 46 gzipped; the compiled page the same), under a raise of each budget by that (`scripts/budget-raises/a-store-never-names-a-change-with-an-id-its-log-holds-*.json`). `capabilities().shipped` gains FR-204.

Compatibility: ops, stored formats, the wire, the declaration and derived tools are unchanged; `capabilities().shipped` gains FR-204. A log written before this may still hold a pair of changes under one id; this does not rename them. What Graview Cloud does: deletes the wake's reopening on the whole log after `receive` (`packages/room/src/room.ts`, INTERIM(FR-204)) once `capabilities().shipped` has FR-204.
