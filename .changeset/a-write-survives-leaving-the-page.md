A change made just before the page navigates or closes is kept. Since the browser adapter moved a store to IndexedDB, a write landed a transaction after `store.apply` returned, so a person who edited and left at once, and the journeys harness that arranged a plot and went to the next page, opened a store without the change. `openStore` now hands every op to the adapter's journal inside the apply, and the browser adapter writes it to localStorage synchronously; the journal holds only the ops IndexedDB has not committed yet, and each is let go of once the log has it and a snapshot that reflects it has. The next open puts back what the journal holds, each op once: the ops the log does not have, by id, are appended to it, and the ops the stored snapshot does not reflect, by seq, are folded onto it. When localStorage refuses even the journal, `onPersistError` is told, and IndexedDB's own write goes on. `pnpm verify journeys` walks seedbed's "Getting from a problem to its repair" jobs again. The `graview-ship` skill says when a page's edit is kept.

Compatibility: ops, the wire, the declaration and derived tools are unchanged. Stored formats: the browser adapter adds two keys per scope, `<prefix>:<scope>:journal` in localStorage (the ops not yet committed, a JSON array, absent when there are none) and `<prefix>:<scope>:through` beside the snapshot in IndexedDB (the seq of the last op the snapshot reflects); a store kept without `through` reads as reflecting none of the journal, which an older build never wrote. `BrowserAdapter.keysFor` answers both, and the adapter gains `journal` and `loadJournal`, which `openStore` calls on any adapter that has them. What Graview Cloud does: nothing; a hosted page persists through its server, not this adapter.
