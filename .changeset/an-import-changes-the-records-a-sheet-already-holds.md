"@graview/core": patch

An import can change the records a sheet already holds instead of making them twice (FR-177). Imported a second time — corrected, a quote raised, an email fixed — the vendors sheet made every vendor again, numbered `-2`. `importRows` and `previewImport` take `match`: `"label"` finds a live record of the kind called what the row would call it, `{ column, field }` one whose field holds what the row has under that column, both under the importer's sight. A row that finds one changes only the fields it has whose value differs, through the kind's `edit-<kind>` so the policy answers as a press on "Change" would, and links what it names that the record lacks (a relation to one replaces the link it had); a row that finds none makes a record as before. Each row says which — "Row 2 would change Bloom & Co (Quote: 1000 → 1200).", "Row 3 would leave Petal Press as is.", "Row 4 would make New Florist." — and a row is refused in words when two records answer to it, when the one that answers is archived, when a row above already makes or changes it, or when it would change a field the edit act does not. The changes, the records made and the links are one batch and one undo. `proposeMapping` suggests a `match` (a key column such as an email or a code, else the column the name is read from) with `matchSaid`, and never applies it.

Compatibility: no surface changes. `@graview/core/import` gains the `match` option and the `ImportMatch` and `ImportChange` types; `ImportResult` gains `changed` and `unchanged`, `ImportRowOutcome` gains `action` (`make`, `change`, `leave` or `refuse`) and `changes`, and `ProposedMapping` gains `match` and `matchSaid`. Without `match` an import makes, says and keeps exactly what it did.
