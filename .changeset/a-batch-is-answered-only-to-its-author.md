**Security.** A batch is answered only to whoever made it. A call sent again under its batch is answered with the ops it made the first time (FR-49), and a batch id is the client's to choose — so Bo, sending a call under Ada's batch, was acked with Ada's ops and his call was never made; and a client could name a batch a host mints for itself (Graview Cloud's `migration:v2`) before the host did, and later take it back as its own. Graview Cloud's spike found it. Now the live wire and `POST /graview/ops` answer a batch only from the asking seat's own ops — the same kind and id, and for an agent the same person it acts for — and refuse a batch that holds somebody else's `invalid`, in words ("That batch is somebody else's: send the change under a batch this client minted."). A client's batch has a shape, what a `Store` mints by default: `batch:<tag>:<n>` or `undo:<tag>:<n>`, the tag up to 24 lowercase letters and digits; any other is refused `invalid` before anything is judged. A call that names no batch lands in one the server mints outside that shape, `served:<kind>:<tag>:<n>`, and so does everything the store `createStoreHandler` opens lands itself. `isClientBatch(batch)` says whether a client may name one, `serverBatchIds()` is the minter a host hands its own store (`new Store({ batchIds: serverBatchIds() })`) so its migrations, seeds and RPCs are in batches no client could claim, and `authoredBy(author, seat)` is the judgement of "the same seat"; all three, and the type `BatchClaim`, are exported from `@graview/ship` and `@graview/ship/runtime`.

Compatibility: the wire and live protocols — narrowing, no field or message added, `WIRE_PROTOCOL` and `REFUSAL_REASONS` unchanged. `openRemote` already sends batches in the client shape, so it is served exactly as before. A client of its own that names batches any other way (`local-a-1`) is now refused `invalid` and should send none, or mint them as a `Store` does; a re-sent batch that holds another seat's ops is refused where it used to be acked. A call without a batch lands in `served:…` where it landed in the store's own `batch:<tag>:<n>`; nothing parses a batch id, so only a host that matched on that shape notices. Ops, stored formats and check codes are unchanged.
