An id a caller asks for says its kind, as a minted one does (Roadmap f-add-id-kind-prefix). An `id` passed to an add act was kept as given (`apt1`) while every minted id carries its kind (`actor:apt29`), so a later call that named the record the way every other actor is named (`actor:apt1`) missed it. The decision: refuse, never rename. A requested id is still kept exactly as asked (f-1-0-client-ids), so an offline batch or an agent's chain that names it again names it the same; one that does not begin `<kind>:` is refused with the id it would be — `Id "apt1" does not say its kind: ask for "actor:apt1"` — and none of its batch lands. An id with another kind's prefix (`threat:apt1` on an actor) is refused the same way. A client's guess (`mintedHint`) that does not say its kind is passed over and an id minted, as a taken guess is. A TypeScript act whose `freshId(label)` names no prefix is unchanged. A declared calendar connection now makes its records `<kind>:<calendar>-…`. Core's tests hold the refusal, the id it names, and that a batch with one unprefixed id keeps nothing.

Compatibility: ops and primitives, stored formats, the wire, the declaration and derived tool names and input schemas — unchanged; records already stored under an unprefixed id keep it. Breaking for a caller that asked a creating act for an id without its kind's prefix: it is refused, naming the prefixed id. What Graview Cloud does: takes this build; its agents and offline batches ask for `<kind>:<slug>` ids, and the refusal's sentence reaches the model as any refusal does.
