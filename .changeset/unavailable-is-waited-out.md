A call that landed is never told to wait, and a host that takes no changes for a while says so. The live socket asked the host's `limit` before it looked whether a call had already landed, so a call sent again after its ack was lost — into a room now busy, or capped — was told `busy` or refused for a change already made. Now the batch is looked up first, on the socket as over HTTP: a call sent again after it landed is answered with its ops, and `limit` is never asked about it. And a host had two words, `busy` with a known wait and a final `limit`, for a room that is read-only for a while — Graview Cloud's quarantine — so it refused, and the person's change was taken back. `limit` may now answer `{ unavailable: sentence }`: refused with the new reason `unavailable` on the socket, 503 with it over HTTP. It is the one refusal that is not final: `openRemote` keeps the change shown and pending and sends it again after its `backoff`, with every call made behind it, until the host takes it; a 503 that says `unavailable` is the host reached, not a gateway away, so the client stays online. `REFUSAL_REASONS` is `forbidden`, `missing`, `invalid`, `limit`, `unavailable`.

Compatibility: the wire and live protocols and the refusal reasons — `REFUSAL_REASONS` gains `unavailable`, a change to a stability surface: before 1.0 a code may be added, and docs/stability.md now says so. Additive for every host that does not answer `{ unavailable }`; a host that does should know that a client before this one reads `unavailable` as final and takes the change back, as it read `limit`, and that a program branching on the four reasons meets a fifth. `LimitAnswer` gains `{ unavailable }`. A re-sent call that already landed is now acked where a socket used to say `busy` or refuse it `limit`: narrower, and only ever toward the answer it should have had. `WIRE_PROTOCOL`, ops, stored formats and check codes are unchanged.
