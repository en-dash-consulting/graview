A connection pass says whom it invited and took off, in its report and the app's history, holds an event over its guest cap, and lets a host read the guests back, Roadmap f-sync-guest-changes-in-history (with request:connection-guests-cap-in-declaration and the framework half of request:read-an-events-guests-back). A Google calendar connection with guests wrote attendees on every event it sent, but sending left no op and `SyncReport` said only `pushed`, so no host could tell who a pass invited, the app's history credited the calendar with nothing, and an agent that turned guests on could not check the result.

Now a `SyncReport` carries `guests`: per record, the addresses a write that reached the calendar invited and took off, and the people the event reaches and left out, and why (`invite-off`, `no-address`, `not-a-person`). A write the calendar refused invited nobody. After the writes go, the pass appends one op per record to the app's history, credited to the calendar (`{ kind: "system", id: "google-calendar", name: "Google Calendar" }`): "Invited Ada to Long run", "Took bo@example.com off Long run", and over several records one batch said "Invited 2 people to 3 events". The op is the smallest honest form the log already carries — no primitives, no reads, no writes, `mutation: null` — marked by one new optional field, `sentOut: { invited, removed, refused? }`, with the event, the guests and each person's addresses in `described`, so a seat kept from any of them is served it withheld. It is never undone: an invitation already went out, and undo says so ("Nothing to take back: an invitation already went out. Change the guests here, and the next pass sends that."); it stands in no other undo's way, and Restore to here leaves it be. A refused write with guests gets a line too ("Did not invite Ada to Long run: google-calendar: HTTP 400: Too many attendees"), once while it is the same write refused for the same reason. `sayReport` says the counts: "invited 2 to 3 events · 1 taken off".

A connection's guests are capped by its declaration: `fields.guests` in its `{ via }` form takes `"max": n`, and `graview check` refuses one that is not a whole number above 0 (`connection-guests-max`). An event a write would invite somebody to past it is held unsent — nothing of it goes — and said: "Dinner has 34 guests; this connection invites at most 20". The calendar transport now passes Google's own error message after the status (`google-calendar: HTTP 413: …`), not the status alone.

A host reads back what a connection kept, from the state it already keeps: `guestsOf(state, declaration, localId)` on `@graview/core/sync` says a record's attendee addresses as both sides last agreed them, those matching nobody here, what the last write sent (addresses, quiet or mailed, when) and the last refusal; `connectionStatus(state, declaration)` says the last pass (when, offline or not, what it applied, pushed, refused, invited and took off), how many records are linked, waiting and held, and every record's guests. The engine keeps them in `SyncState.guests` and `SyncState.lastPass`, stamped with the clock a connection is handed (`SyncOptions.now`).

Taking a host-made op's `described` and `sentOut`, and undo's sentence for a line of what went out, cost a hosted page 0.3 KB more up front (350 bytes minified, 113 gzipped), and a page handed a compiled app 0.3 KB (350, 131), under raises naming this changeset; the pages face alone and a visitor's form alone and handed a compiled app 350 bytes minified each, every face 690 / 299, the embed with the studio handed in 643 / 283 and Cloud's worker 12_446 bytes, each under a raise of its own.

Compatibility: ops and primitives — one new optional op field, `sentOut`, on a new kind of op with no primitives and no new primitive; a log holding one folds the same on every build, and a build before this one keeps the field on an op it receives and reads it as a change that touched nothing. `AppendOp` may carry `described` and `sentOut`. Stored formats — a `SyncState` may carry `guests` and `lastPass`, still format 1, which an older build drops. The wire — unchanged. The declaration and check finding codes — a calendar connection's `fields.guests` `{ via }` form gains the optional key `max`, which a build before this one refuses by path; one new error, `connection-guests-max`; no declaration that passed is refused. Derived tool names and input schemas — unchanged. `SyncReport` gains the optional `guests`; `SyncOptions` the optional `guests` and `now`; `SyncMapping` the optional `name`.

What Graview Cloud does: on this version its connections' passes leave the guest lines in each app's history with no change of its own, its Connections page and room can word `SyncReport.guests` and drop the `guestCapped` stand-in and the `TOO_MANY_GUESTS` rewrite for `"max": 20` in the declarations it writes, and its MCP half of reading an event's guests back is `guestsOf` and `connectionStatus` over the state it already keeps per connection.
