A worker view keeps small values for whoever is looking at it, and one sign-in can be several people at one screen (Roadmap f-viewer-state-and-me-framework). Children on one shared tablet need their own progress in a family's app, and each visitor to a demo their own, and until now an app held only records, shared by everyone who may see them, and a reader's settings.

`graview.mine.get(key)` answers a string or `null`, `graview.mine.set(key, value | null)` keeps a string of at most 4 KB or forgets it, and `props.mine` holds them at draw time, so a first draw needs no round trip. A value past 4 KB, anything but a string or null, too many writes in a minute for one view, or one a host will not keep, rejects with a sentence, which `onProblem` hears too, never quoting the value. They go to a host's `ViewerState` — `{ read(view), write(view, key, value) }`, answering `{ ok: true }` or `{ ok: false, sentence }`, handed to `mount`, `<Embed>`, `PagesApp`, `<Shell>` and `GraviewProvider` as `viewerState`, and to `mountWorkerView` — and without one they last the visit, in the page's memory, per view and per viewer. A host slow to read does not hold the first draw past 1.5 s: the values are pushed if they come, and until then `get` and `set` reject in a sentence. A write past 10 s rejects as "not kept yet" and may still land, and a later write to that key waits for it to settle and then sends only the newest, even from the next drawing of the view on the page, which is pushed what was kept. So on one page an older value never lands over a newer. Two tabs are two lines: a host that wants the same across tabs takes each key's writes in the order it wants them. A host that never answers a write costs a key's asks one wait, then none, leaves later values for that key unkept and in no `props.mine`, and holds at most 200 keys open. A view asks by key alone and the host says its name, so another view's values are not reachable. They are not the graph's: no op, no history, no undo, no export, no agent's tool, and a headless run is handed none. A draft keeps its own for as long as it is drawn, and reads and writes nothing kept for the view it would replace.

A seat may carry `profile: { id, name }`. `$me`, a view's new `props.me`, and a sight `via` the people or `own` then read that profile's person: a record of the people kind, made by the first act in that act's own batch (a refused act makes none, an act that does nothing leaves none, and undoing the act leaves it), with the id `<account>~<profile id>`, so it is linked to the account by what it is called. No profile can name a member's record or another account's: a profile id holds no `~`, a seat's requested id with one is refused, as is one its code act hands `addNode` or `emit` (a system author's is not, being the host's own, which `applyPrimitives` could write as well), a client's id hint with one is ignored, a record of another kind there from a restore is not read as the person, and an account whose own id holds one has no `$me` and owns nothing by id. A profile with a bad id or a name with nothing visible in it is no profile, and its name is held to 200 characters, on the seat, the op's author, whichever way the op was made, its sentence and the person. What the seat may do stays the account's: its roles and grants are read as they were, a person made in the act is no way past `ownEnd`, since the act is judged again once it is there, and `self` and `ownEnd` read both the account's record and the profile's person as its own. History and presence, on every path, say "Mia (Nick)".

A person removed stays removed. Their id is not made again, `$me` refuses as it does for a member with no record ("is done as you, and you have no record here"), and the act is not offered: a host that retires a profile by removing its person retires it for good under that id. So too where the people kind requires more than a name: no person can be made, `graview check` says so (`people-unmakeable`, a warning, where an act says `$me`), and a profile is not offered that act. A code act that says `doneAsMe: true` is treated the same; one that only reads `ctx.me` is offered, since nothing can tell before it runs, and refused in those words. What a seat already did it may still undo. In an app with no people kind there is no person to be: `ctx.me` is the account's id, with a profile or without. Without a profile nothing changes, except that a view whose seat has a person record in its sight is now told so in `props.me`. A served store reads a profile from `x-graview-profile` and `x-graview-profile-name` exactly when it believes the seat's headers, and otherwise from its host's `seatOf`.

A hosted page carries 3.7 KB more up front, and one handed a compiled app 3.5 KB.

Compatibility: ops and primitives — an op's author may carry an optional `profile`, and the first act of a seat with a profile adds one op, with no act, that makes its person (`docs/stability.md`). A downgrade reads such a log and folds it the same, ignoring `author.profile` and reading `$me` as the account, but its undo counts that op as part of the batch: it takes the person back with the first act, or refuses where a later act stands on the person; another seat with the act's grant is refused undoing that batch; its batch sentence says "Mia joins"; and an undo made there outlasts it, since this build then reads the person as removed for good and refuses that profile's `$me`, the account's own unaffected. Stored formats — unchanged. The wire — new: the guest protocol's `mine` request and `mine-answer`, a frame's host dropping the request unread, `GuestProps.mine` and `GuestProps.me`, and the seat headers `x-graview-profile`, `x-graview-profile-name`, `x-graview-for-profile` and `x-graview-for-profile-name`. The declaration and check finding codes — new: `people-unmakeable`, a warning; and a seat's requested id, or one its code act adds, holding a `~` is now refused. Derived tool names and input schemas — unchanged, except that a seat with a profile that has and can have no person is not offered an act that says `$me`. The JavaScript API — new, optional: `ViewerState`, `viewerState`, `SeatProfile`, `Author.profile`, `meOf`, `profileOf`, `profilePersonId`, `meIn`, `withValidProfile`, `graview.mine`, `mountWorkerView`'s `draft`, a worker view definition's `keepsNothing`, a mutation's `doneAsMe`.

What Graview Cloud does: implement `ViewerState` over `viewer_state` and `/graview/mine` and hand it to the mount as `viewerState`, bound to the seat's viewer id, with its caps said as sentences; say `profile: { id, name }` on the principal `seatOf` returns (and on the client's `principal`), and key a socket's seat by it (`seatKey`); expect a profile's person at `user:<account>~<prf_id>`, and rename it with the member's own (`people.ts`) if a profile's name changes, since the framework only makes it. Retiring a profile by removing its person is for good under that id: `$me` then refuses and is not offered, so a profile brought back takes a new `prf_` id. An account id holding a `~` has no `$me` where a kind is the people: check none of yours do. A record may hold one where your own system author, a sync's mapping among them, asks for it; a seat's act may not.
