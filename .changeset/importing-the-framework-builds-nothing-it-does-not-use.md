Importing the framework builds nothing it does not use (Roadmap f-smaller-worker). Graview Cloud's Worker paid about 50 ms of CPU on every cold start before it answered, and most of what the framework added to that was zod: the document format built some hundred and fifty schemas the moment `@graview/core/document` loaded, the edit ops another sixty, a template's and a connection's shapes more, and nineteen framework modules imported zod's `z` by name, which makes esbuild (and so wrangler) keep every part of zod and its forty-odd locales, 805 KB, whatever was called. The document's shapes (`DocumentSpec`, `KindSpec`, `FieldSpec` and the rest), `TemplateSpec` and `ConnectionSpec` are now `z.lazy` over a set built the first time one parses, the edit ops' shapes are built with the first edit, and the framework imports zod as `import * as z from "zod"`, which a bundler shakes to what is called. Bundled as wrangler bundles it, what Cloud's worker imports from the framework comes to 1.8 MB instead of 2.4 MB, 219 KB of it zod's instead of 805 KB, and loads in 29.5 ms of CPU instead of 52.3 ms; `@graview/core/document` alone in 10.8 ms instead of 34.3 ms, `@graview/core/check` in 13.9 instead of 37.9. `node scripts/import-cost.mjs` measures each entry Cloud imports in a fresh process (`--bundled` as a Worker receives it, `--worker` the names it imports together, `--profile` where the time goes), and `tests/importing-the-framework-costs-little.test.ts` holds each to a budget of CPU, the names Cloud imports to 2 MB and 260 KB of zod, and every framework module to the namespace import. A hosted page spends 1.2 KB more up front on the lazy shapes (0.7 KB handed a compiled app), raised by what they measured (1_197 / 356 and 691 / 143); the scene and the pages faces before they draw are raised to 960 KB.

Merged onto the scheme's logo in the same release, the two together carry 0.0 KB more up front than each alone, on a hosted page and on one handed a compiled app.
Compatibility: ops, stored formats, the wire, the declaration and check finding codes, and derived tools are unchanged; `document.schema.json` is byte for byte the same. The document's exported shapes keep their names, their parse and their issues, but each is now a zod lazy schema over the shape it was (`DocumentSpec._zod.innerType` is the object schema), so code that read an object schema's own members off one (`.shape`, `_zod.def.shape`) reads them off `_zod.innerType` instead. `@graview/core` still re-exports `z` for a product.
