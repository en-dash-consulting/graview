A derived edit offers every field nothing else really sets, and refuses what it cannot take (FR-110). From building En Dash Org on Graview Cloud: `note-strength` acts on a person and makes a strength named `$name`, and declared no `writes`, so the framework guessed from its argument names that it wrote the person's name — "Change the person" offered notes and role, and a person could never be renamed. A document's act now always says its `writes`, read off what its `sets` and effects set on its subject, `[]` when that is nothing; an argument that feeds a record the act makes, or any record but its subject, is not a write of the subject. The name-match guess is kept only for a TypeScript mutation that declares no `writes`, whose `apply` cannot be read without running it. The derived `edit-<kind>` input is strict: `edit-person { id, colour }` is refused as invalid with "does not take "colour"; it takes "id", "name", "role", "notes"" where it used to parse to `{ id }`, and any act's unrecognised argument is said that way. `edit-person { id }` is refused with a typed `ActRefusal` (reason `invalid`, its `sentence` the words a person reads) rather than a bare `Error` a host could only call its own failure; `ActRefusal` is exported from `@graview/core` and is the same class `@graview/core/document` has always exported, so a document act's refusals and a derived edit's are one type, and `refusalOf` reads its reason.

Compatibility: unchanged for stored data, ops and the wire. A derived tool's input schema changes for an unchanged declaration: every `edit-<kind>` says `additionalProperties: false`, and a document whose act made a record with an argument named like a field of its subject (Cloud's vendor shortlist's `add-to-category` and `name`) now offers that field on `edit-<kind>` — announced for the `document:vendors` and `document:two-lines` conformance fixtures. A compiled document act's `writes` is `[]` where it was absent. `capabilities().shipped` gains `FR-110`.
