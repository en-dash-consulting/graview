A view's check knows the place of a titled view the host keeps, and `describePlace` describes that place (Roadmap f-check-view-places). Threat Watch, on Graview Cloud, keeps a view of many threats titled "Live threats", drawn at `/places/live-threats`; its home linked there with `<a data-place="live-threats">`, the link worked on the page, and `propose_view`'s check said "It names the place "live-threats", which this app does not have" — a false warning that teaches a chat to stop writing `data-place`. The check was handed the document's places and never the host's views, and `describe_place` said the place was not one the app has. Now `runWorkerViewHeadless` takes `views`, the manifests of the views the host keeps — the list `placesOf` and `describePlace` already take — and each titled view of many is a place at the slug the router gives it, through `viewPlaceOf` on `@graview/core/seat`, the function `placesOf` itself reads, so a `data-place`, a `graview.navigate` or a press on a link naming one is no problem; the view being run is a place of its own when it is titled. A name none of the places is still goes nowhere and says so. A run that is not handed `views` cannot know the host's views' places, so it no longer says such a name for certain: "It names the place "live-threats", which is none of the places this run was told of. … This run was not handed the views the host keeps, so a titled view's place is not among these: if it names one, the link goes there." `graview view check` hands `views: []`, since the app's registered views are its places already, and says what it said before. `describePlace` handed `views` finds a titled view's place by its slug, its title or its address, and says it as it says a lens's: its title, slug and address, drawn by `view:<name>`, one `{ t: "view" }` part with the view's title, whether it flows with the page or keeps a frame of its own (`flows`, only where the host said), and the parts a headless run drew; its text says `[the view "Live threats", flowing with the page]` and what the view drew under it. `graview-view-links` says a titled view's place is a place a link may name, and `graview-host-page` that `describePlace` and `runWorkerViewHeadless` take the views. `core`'s tests describe a titled view's place by slug, title and address, flowing, framed and unsaid, and none where the host names no such view; `guest`'s find a `data-place` and a navigate naming a titled view's place not flagged and a press on it opening it, a slug naming nothing still flagged for certain, a run without the views saying it as a doubt, and the place a run drew described.

Compatibility: additive in the API — `runWorkerViewHeadless`'s `views`, `viewPlaceOf` on `@graview/core/seat`, `DescribedHostView.flows` and `hidden`, and `flows` on a `{ t: "view" }` part. A behavior change in a headless run that is not handed `views`: a `data-place`, a `data-record` or a navigate naming none of its places is said as a doubt rather than as no place of the app, and a titled view's own place is among its places; `describePlace` handed `views` describes a titled view's place it refused before. The manifest, the declaration, the wire, the stored formats and the derived tools are unchanged.
