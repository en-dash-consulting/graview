# What a version may change

Graview's stability promise says what a release may change and what it may not. Every `@graview/*` package shares one version; this page is `docs/stability.md` in the repository.

## The promise

A host runs thousands of stored apps on one build of `@graview/*`. Before it takes a new version it needs to know three things: whether stored data folds the same, whether a declaration that compiled still compiles, and whether the tools a model calls moved. This page is the promise, and `capabilities()` is how a host reads what a build ships instead of guessing from a number.

Every `@graview/*` package shares one version (a changesets `fixed` group). Before 1.0, a minor may break what this page allows a major to break; each break is still said in a `Compatibility:` line. From 1.0 on, the rules below hold within a major.

### The five surfaces

#### 1. Ops and primitives: the stable contract

An `Operation` and its `Primitive`s are history, and history is never rewritten. Within a major:

- Never changed incompatibly. A field may be added if it is optional, and an op without it reads as before (`via`, `author.name`, `author.onBehalfOf` arrived this way).
- No field is removed or changes meaning. No primitive is removed.
- A fold of the same log gives the same graph on every version of the major.

- An op may say what it was based on (FR-172): `lineage: { basis, confidence?, model? }`, a basis of 1–500 characters, a confidence from 0 to 1 and a model name of 1–120, given as `ApplyOptions.lineage` (or on `AppendOp`) and checked before anything is kept; a store refuses one that is not a lineage with a `GraphError`. An undo of an op that carried one keeps it as `undoneLineage`, so a host reading the log can tell a suggestion was declined without the op it took back. `Batch.lineage` is its first op's. Both fields are optional and additive within op format 1: an op without them reads and folds as before, and a build that predates them keeps them on an op it receives and draws nothing of them. A link whose making op carried a confidence below 1, by any author but a person, is PROVISIONAL until a person's op takes it away and puts it back — `keep-link` (`KEEP_LINK`, `{ kind, from, to }`), an act every store answers to and no list of acts offers, permitted to whoever may run an act whose `connects` or `severs` names the link's relation (or a grant naming `keep-link`; before 0.1.29 any act that made or broke links or made records sufficed), and refused as `missing` to a seat that may not see either end, alike whether the link is there or not (FR-55) — or the link is taken away; an undo of that keep makes it provisional again. `linkProvenance(store, edge)`, `isProvisional`, `provisionalLinks` and `provenanceWords` (`@graview/core/provenance`) are the one answer every face and host reads; nothing in the framework decides what to link.
- Text is typed together (collaborative text, phase 2) with no new primitive and no new op field, where `@graview/core/typing` is loaded — `@graview/ship`'s server and runtime entries load it, and a page loads it when it types; without it a store answers to no `type-text`, writes a whole value as written and undoes as before. A keystroke is `type-text` (`TYPE_TEXT`, `{ node, field, at, remove, insert, rev? }`, offsets in UTF-16 code units against the field's text at revision `rev`), an act every store answers to once that is loaded (a store made before too) and no list of acts offers, permitted to whoever may run an act that writes that field of that record (a declared act whose `writes` names it, or the kind's `edit-<kind>` and what that rides, or a grant naming `type-text`), judged under the caller's sight. The store reads the text at `rev` back off the log and carries the keystroke over every `splice-text` since, writing one splice; the first keystroke into a field holding no text (absent or empty) writes the text it inserts whole, wherever it said it was, as a `patch-node`, so its inverse is exact. It refuses as `invalid` a field that is not typed together, offsets the text read then does not have, and a keystroke against a field written whole since `rev` or a `rev` behind the log's horizon; a field kept from the caller reads to it as holding no text, so its keystroke is a whole write, refused as an argument the act does not take whatever the field holds. Which fields are typed together is the declaration's (`markCollaborative`; read by `isCollaborativeField` on `@graview/core/typing`): a Markdown field, a document's `text` and a string declared to hold more than 500 characters are, unless marked otherwise; a short string is not. A `patch-node` that any act, an edit, an agent or `applyPrimitives` writes to such a field holding text is written as the one `splice-text` that makes the change — against the text at the revision the call's `ApplyOptions.base` names for the field (a three-way merge, carried over what others typed since), else against the text now — so a log written by this build holds splices where an earlier build wrote patches, and folds to the same graph. A splice claims no base (`baseFor` skips a field typed together, and so does `openRemote`), so a stale write is a conflict only for a field that is not typed together. Undo carries the inverse of a person's splices over the splices of the same field since (`undoneInverses`; `undoPrimitives(ops, log)` reads the same): a later splice on that field does not block it, and text someone else since deleted shrinks out of what it takes back; a later whole write of the field, or the record's removal, still blocks it.
- Typing is said, not stored, in words (collaborative text, phase 5): nothing in the log changes. A run of typing is the ops of one `type-text` batch, and one person's consecutive runs into one field — no other gesture between them in the log — are one change wherever a change is said: one tick of `ticksOf` (`batches`, `typed`), one row of Activity, one entry of `historyInWords`, said "Ada wrote in Kitchen's notes (+42 −3)", characters counted as a person counts them. A notification of such a field says what was put in and taken out (`MatchedRecord.fields[].typed`: `inserted`, `removed`, `spans`) and never its text before and after, and a run is told once: `holdTypingRuns` holds a match that is a run of typing until its typist has stopped for `TYPING_QUIET_MS` (5 s, a host's to set) or another match for the same subscription comes, which is told after it — `watchSubscriptions` and `@graview/ship`'s handler hold through it, and tell what they hold when they stop. Within the major a subscriber hears of a run at most once and never later than the quiet interval after its last keystroke, the counts and spans keep their meaning, and the sentence is display only, like an op's `intent`.

A major that must change them ships `upgradeOp` steps (below).

Op format 2 (0.1.43, before 1.0) took one field away: an op keeps no `inverse`. It was its primitives inverted, newest first, written down beside them, so every value an op wrote was in the log twice more — a 19 KB picture changed in a field was a 95 KB op, and is now 57 KB. What puts an op back is `inverseOf(op)`, worked out from the primitives where it is read (undo, a rebase's rollback, playback, verifying a fold) and remembered per op. `Operation.inverse` stays as an optional field for one case only: an op read from format 1 whose stored inverse was not its primitives' own (a host could hand `append` one), which is kept and is what undo puts back. `AppendOp.inverse` is gone. The same log folds to the same graph, and undoes to the same graph, in either format.

FR-173 added one optional field and no primitive. An archived record is said on the record itself, `$archived: true` (a key no declared field can take), written and taken off by an ordinary `patch-node`, so archive and unarchive fold, undo and travel through every adapter as any patch does. The op of a merge carries `mergedInto`, the id of the record the duplicate went into; an op without it reads as before. A version before FR-173 folds the same log to the same graph, and reads an archived record as a live one with one more key.

The app's own actor (0.1.30) added two optional op fields, one optional author field and one record mark, and no primitive. A suggestion that waits is an op with `suggests: MutationCall[]`, its `lineage`, and no primitives (`suggest(store, calls, options)`, `@graview/core/tidying`): it folds to nothing. Accepting it applies the calls as an ordinary change whose `lineage.suggestion` names the suggestion's op; declining it is an ordinary undo of that op, with `undoneLineage`. An author may say `automated: true` (a `system` or `agent` author: the app's own actor), which the store holds to what a person declined, to records left alone and to the declaration's `tidying`. A record left alone is `$leftAlone: true` on the record, written and taken off by an ordinary `patch-node`, as `$archived` is. A version before folds the same log to the same graph, keeps the fields on an op it receives, and lists a suggestion's op as a change that touched nothing.

Settled for 1.0 (0.1.49): what a suggestion and a lineage keep is promised as below, and changes only as the rules above allow.

- A suggestion is an op with `suggests`, `mutation: null`, no primitives and its `lineage`; accepting it is a change whose `lineage.suggestion` names it; declining it is an undo of it, with `undoneLineage`. These never change meaning: a log written by any build since 0.1.30 folds, waits and refuses the same (`packages/core/tests/fixtures/formats/suggestions-0.1.48.json`).
- A suggestion may say when it stops waiting: `expiresAt`, an ISO time, on its op (`SuggestOptions.expiresAt`). From then on it is not waiting — not in `suggestions`, not accepted nor declined — and nothing is undone; the same calls suggested again are a new suggestion. An op without it waits until a person answers it. A build before 0.1.49 keeps the field and reads the suggestion as waiting.
- "Not now" is not in the log. A `Dismissal` (`{ suggestion, at, until? }`) is the person's own state, kept where the host keeps what a person chose and handed to `suggestions(store, principal, { dismissed })`; it hides the suggestion from that person, until `until` when given, and binds the app's own actor to nothing. Only a decline — an undo in the log — answers a suggestion for everyone and refuses the actor the same change again.
- A decline refuses the same change by what it means as well as exactly as asked (`meaningKey`, `suggestionKey`): a link of one relation between the same two records whichever act asks it, a merge of the same pair either way round, a record archived, unarchived, removed, left alone or let be tidied by any spelling of the act, and any other call by any spelling of its act with the same arguments, less the `id` of a record an act that `creates` would make. Both keys are worked out from the calls whenever they are asked, so nothing is stored for them, and a decline already in a log matches by both. A later version may only widen what a decline catches.
- A lineage is `{ basis, confidence?, model?, suggestion?, interaction?, actor?, run?, evidence? }`: `actor` the automated actor or judge that made the call, `run` the pass it was made in (one id for a night's work, so it reads as one unit), each 1–120 characters, and `evidence` at most 50 ids of the records its basis rests on, which an op names as it names any id, so a seat that may not see one is served the op withheld (FR-55). A key a build does not know is a later build's: kept as JSON keeps it (a copy, written out and read back), on the op, in the log and on the wire, when JSON can write it, it is not named `__proto__`, `constructor` or `prototype`, and the whole lineage is at most `LINEAGE_LIMIT` (4000) characters written out; anything else is refused with a `GraphError` before anything is kept. Before 0.1.49 such a key was dropped where the store checked a lineage. A later version may give a kept key a meaning; it never takes one away.
- A vote on a suggestion (0.1.62, Roadmap f-suggestion-votes) is an op of the built-in `vote-suggestion` act (`VOTE_SUGGESTION`, `{ suggestion, vote: "for" | "against" | null }`), which every store answers to and no list offers, as `keep-link` is: `mutation` the call, no primitives, the vote on the op (`Operation.vote`), and the records the suggestion names as `described`, so a seat kept from one is served the op withheld, as the suggestion is. One standing vote per person — the `actingAs` id, so an agent votes as the person it acts for — the latest in the log; `null` withdraws it; an undone vote never counted. `suggestions()` carries each suggestion's `tally: { for, against, mine? }`, and `votesIn` and `tallyOf` (`@graview/core/tidying`) read it off a log. An undo of a vote is its voter's, the system's, or a seat's the policy grants every act. A lineage may name `voters` (at most 200 ids of 1–120 characters): who had voted for a suggestion the app's own actor made at the declaration's `tidying.autoAcceptAt`, in the deciding vote's own batch, with `suggestion` naming it as any acceptance does. A build before it keeps the field on an op it receives, folds the same log to the same graph, lists the vote as a change that touched nothing, and counts no tally.
- A suggestion of several changes (0.1.63, Roadmap f-job-approvals) may keep each call's sentence in `suggestsSaid` (a string per call of `suggests`, in order), and a change that accepts some of a suggestion's calls rather than all names their places in it as `lineage.items` (at most 500 whole numbers): the rest still wait, `suggestions()` lists them as `items: { at, call, intent }[]` with the maker's `batchIntent` as `headline`, and a decline after that is a decline of the calls not yet taken. An acceptance without `items` takes every call still waiting. A workflow whose `approve` is "ask" leaves one such suggestion per run, its lineage naming the run (`lineage.run`, `lineage.actor: "workflow:<name>"`). A build before it keeps both fields, lists the suggestion's calls whole and reads a partial acceptance as the whole suggestion taken.
- A vote from a seat no one person holds (0.1.63, Roadmap f-votes-shared-seat) is refused by the store on every path — the wire, a socket, an RPC, a store with no policy — in the words "Sign in to vote on this suggestion.": a principal the host marks `shared: true` (every signed-out visitor served as one), a `visitor`, or an agent acting for either. Where the host says `votes: { advisory: "visitors" }` (`StoreOptions.votes`, the handler's `votes`) and the seat names its visitor (`Principal.visitorKey`), the vote is kept instead, its op's `vote` carrying `advisory: true` and `voter` (that key): one standing vote per visitor, counted apart in `tally.advisory: { for, against }`, never toward `autoAcceptAt`, and only that visitor's (or the system's, or a seat's the policy grants every act) to undo. A build before it reads an advisory vote's op as a vote of the shared seat's.
- A suggestion's op may now have a person as its author (0.1.63, Roadmap f-proposals-for-review): a proposal is the same op — `suggests`, `mutation: null`, no primitives, its lineage — made by the built-in `propose-changes` act (`PROPOSE_CHANGES`, `{ calls: MutationCall[], intent? }`), which every store answers to and no list offers, as `vote-suggestion` is. Its author is the person (or the agent acting for them), and its lineage names them as `proposedBy` (1–120 characters, the `actingAs` id), with their words as `basis`, else "Proposed by <name>". The call is permitted where each call it holds is one the seat may run or a grant's `propose` names; its calls are rehearsed as the store would judge them for whoever accepts it. Accepting it is a change by the reviewer whose lineage carries `suggestion` and `proposedBy`; declining it is an undo whose `batchIntent` says "Declined <name>'s proposal: …"; its proposer withdraws it with an undo that is no decline. A build before it reads the op as any suggestion's, keeps `proposedBy` as a lineage key it does not know, and refuses the `propose-changes` call as an act it does not have.

- What a connection sent out is history (Roadmap f-sync-guest-changes-in-history): one new optional op field, `sentOut: { invited, removed, refused? }`, and no primitive. After a write with guests reaches the calendar, a pass appends one op per record — credited to the connection's system author (`{ kind: "system", id: "google-calendar", name: "Google Calendar" }`), `mutation: null`, no primitives, no reads, no writes, its sentence ("Invited Ada to Long run", "Took bo@example.com off Long run") reading the event, the guests and each person's addresses in `described`, so a seat kept from one is served it withheld — in one batch for the pass, said over several records as "Invited 2 people to 3 events". A write the calendar refused, or the connection held over its `max`, is said once the same way with `refused: true` ("Did not invite Ada to Dinner: …"). It folds to nothing; it is never undone (`checkUndo`: "Nothing to take back: an invitation already went out. …"), stands in no other undo's way, and "Restore to here" (`restoreBatches`) leaves it be. A build before it keeps the field on an op it receives and reads the op as a change that touched nothing. `AppendOp` may carry `described` and `sentOut`.

##### Failing closed: what a reader does not know (1.0)

- **An unknown primitive is refused, never skipped.** The six primitives are `PRIMITIVE_OPS`. A new one raises `FORMATS.op` and travels only to a reader that said it reads that format (`opFormat`, §3), as op format 2 did. A reader that meets a primitive it does not know anyway — a log a newer build wrote, an op handed over by hand — refuses it with `NewerFormatError` (`what: "op"`, `unknown: 'primitive "<name>"'`) wherever ops are folded: opening a log (`OperationLog`, `Store`), receiving or rebasing onto ops, folding a graph (`Graph.applyPrimitives`, all or nothing), a seat's view of the log, a migration's fold, `upgradeOp`. It used to be skipped where a fold switched on the five, so an older reader's graph diverged from the log without a word. A planned primitive such as `splice-text` for collaborative text ships at `FORMATS.op` = 3 on this path.
- **A typed value is reserved, as `$archived` is.** A field's value that is an object with a `$type` — `{ "$type": "rich-text", … }` — is a typed value, and `VALUE_TYPES` names the ones this build knows (none yet). Applying an op that writes a typed value whose type the reader does not know is refused with `NewerFormatError` (`unknown: 'value type "<type>" in "<field>"'`), the record left as it was, because writing it as an opaque object would let the next edit through that reader mangle it. Whatever only passes a value along — the log, every adapter, an export bundle, the wire, a seat's view of an op — keeps it exactly as written. An object without a `$type` is an ordinary value, as before. A new value type arrives with a new op format, like a new primitive.
- **An author's kind is open.** `AUTHOR_KINDS` is `human`, `visitor`, `agent`, `rule`, `system`. `visitor` (1.0's foundation) is a person who never joined the app — one answer to a form a host opened — and is what `formVisitor` mints, held to the form's role as a person is to theirs; a visitor's op said `human` before, and reads as it did. A kind may be added within a major, and a reader that meets one it does not know reads it as `system` for display and policy (`authorKindOf`) — the app itself — and never refuses the op, which is history and folds the same whoever wrote it; the log keeps the kind as written. A seat is the host's to mint, so a kind its headers name that a build does not know is a person's seat (`human`), never the system's. The app's own actor is a `system` or `agent` author with `automated: true`, not a kind of its own.
- **An op's `intent` is display only.** It is the sentence a person reads; nothing in the framework matches on its words, and a program must not. What an op did is its `mutation`, its primitives, its `batch` and its `undoes`: ship reads a migration's version from its batch (`migration:<from>-><to>`), not from its sentence.

##### A link's own id and data: reserved (1.0)

A link is `{ kind, from, to }`, one per kind per pair. It may also carry an `id` of its own and `data`, a JSON object (`GraphEdge`), so the day a link has a weight, a role or an order nothing stored is rewritten. Both are optional and additive within op format 2, and no format number moves.

- **Kept and folded everywhere.** An `add-edge` that carries them is kept as written by the graph, its snapshot, the log, the wire, a seat's view of an op, an export bundle and every adapter: memory, file, browser and SQLite whole as JSON; the SQL adapters in the edge table's optional `data` column (`{ id, data }` as JSON), which `createTables` adds to a table made before it. An app's table without that column reads and writes links as it always did, and refuses a link that carries an id or data rather than keep it without them. `snapshotHash` counts them when a link carries them, so a graph without them hashes as before. A merge moves a link whole; a migration that moves a link to several heirs gives each the data and none the id.
- **Removed by id when it names one.** A `remove-edge` whose link carries an `id` removes the link holding that id — the graph's own, and a migration's fold — and one that names no id removes by kind, from and to, as before; an id no link holds is `missing`. An act that removes a link by its id is handed the link as held, so the removal's inverse puts all of it back.
- **What a write is held to** (`EDGE_FIELDS`): an id of 1–200 characters with no space or control character, unique among the links; data a JSON object of at most 4,096 characters as JSON.
- **Reserved, not open.** No act the framework derives writes them, and no face shows them. A second link of one kind between the same pair stays refused (`EDGE_FIELDS.sameKindPerPair` is 1): the same link again is nothing new, as it always was, and one that says it is another — an id of its own — is refused, as is an id another link holds. A version may open several links per pair within the major, since every reader already tells two apart by id; that is additive, and the changelog says so.
- A build before 1.0's foundation folds the same log to the same graph — it keeps the edge object an `add-edge` hands it — but removes by kind, from and to, which is the same link while there is one per pair.

#### 2. Snapshot and log formats: versioned

What is stored carries the format it was written in (FR-31). `FORMATS` names the current formats (`snapshot`, `op`), and `formatStamp()` gives `{ framework, formats }`. A store's meta and every bundle are stamped with it.

- A reader meeting a newer format says so with `NewerFormatError` and does not fold it. The host refolds from the log or rolls forward. Rollback is therefore always safe: the previous version never misreads what the next one wrote.
- An older format is brought up by `upgradeSnapshot(snapshot, from)` and `upgradeOp(op, from)`, one step per format change. Each step ships with a test over a fixture of the format before it (`packages/core/tests/fixtures/formats/`).
- Anything written before stamps existed (0.1.0) is format 1.
- Op format 2 (0.1.43) writes no `inverse`. A format-1 op reads on every later build: `upgradeOp(op, 1)` drops an inverse that is its primitives' own, and a store does the same to every op it opens on, receives or rebases onto (`bareOp`), so a store's log is format 2 whatever wrote it. Nothing on disk is rewritten to open it: a format-1 log opens, undoes and goes on, its old lines with their inverses beside the new lines without, and a compaction rewrites what it keeps in format 2. A store's meta is stamped `op: 2` when it opens, so a build before 0.1.43 meeting it refuses it with `NewerFormatError` ("Upgrade the framework to read it") rather than undo an op it finds no inverse on; a bundle exported by 0.1.43 is stamped `op: 2` and refused by an older `assertBundle` the same way. A host that must roll a store back to an older build writes its log out with `withInverse(op)` and stamps it `op: 1`.
- Snapshot format 2 is a stored state whose checkpoint keeps the app as readers are, or may again be, served at a seq behind it (`Epoch.published`, Roadmap f-publishing-lifecycle): a checkpoint past the publish standing at its seq, or past a seq a later publish took readers back to. Only such a store is stamped 2: `formatStamp(checkpoint)` reads the checkpoint a store or bundle begins at (2 when it carries `published`), ship's `openStore` stamps the meta at open and when it compacts (before the checkpoint lands when it moves to 2, after when it does not, so a failed write leaves a store stamped newer, never older), and `exportBundle` stamps the bundle. Every other store — never compacted, live, or compacted with `format: 1` — is stamped 1, as before. A build before it refuses a format-2 meta or bundle with `NewerFormatError` rather than serve readers changes never published; a host that must roll back asks for format 1 by name (`CompactOptions.format`, on `store.checkpoint` and ship's `opened.compact`): the horizon is held at the earliest seq readers are served behind it, wherever the days, the ops and the pins would have put it, and the checkpoint's `seq` says where it stopped. A pin at `store.publishedSeq` is not enough on its own: it holds the horizon at or before the latest publish, and one that lands between two publishes keeps the earlier one and is format 2 with it. A format-1 snapshot reads as written (`upgradeSnapshot(snapshot, 1)` is the same snapshot). A host that keeps its own meta stamps it with `formatStamp(store.log.horizonEpoch())`.
- Op format 3 (collaborative text, phase 1) adds one primitive, `splice-text`: `{ op, id, field, at, removed, inserted }`, part of one text field changed — at `at` (UTF-16 code units) the field holds `removed`, and `inserted` takes its place. It keeps the text it removed, so its inverse is the same splice turned round, and a fold refuses one whose text is not there as a corrupt op (`GraphError`). Nothing is taken away: `upgradeOp(op, 2)` reads a format-2 op as written. A store's meta is stamped `op: 3`, so a build before it refuses to open it with `NewerFormatError` rather than meet a splice it would refuse part way; a host rolling a store back refolds it from the log on the older build. The transform (`transformSplices`, `composeSplices` and `diffSplice` from `@graview/core/typing`; `transformCaret` and `applySplice` from `@graview/core`) is pure and settles a tie the same way on every build of the major: where two splices touch, both insertions stay, the one further left first and, at one offset, the one earlier in the log first.
- A log compacted behind an undo horizon (FR-23) is not a new format. Its ops are ops, its checkpoint is an epoch marked `horizon`, and the archive sits beside it. A build before compaction refuses such a store on open, because its log no longer begins at seq 0. It never misreads one.
- A checkpoint keeps who made each record behind it (`Epoch.creators`, record id to seat id), so an `own` sight knows them after a restart without the archive. The field is optional and additive within format 1: a checkpoint without it opens as before and knows its makers from the horizon on, and a build that predates it ignores it, folds the same graph and judges sights as it always did. A build that predates it and compacts again writes its next checkpoint without the field. Epochs are never served to a seat, so the ids it names stay with the host.
- A checkpoint also keeps what kind each record removed behind it was (`Epoch.removed`, record id to kind, `{}` when there is none) and who wrote each field of its graph that names a record (`Epoch.writers`, record id to field to seat id), so a store opened on it judges a field naming a removed record, and a seat's own words, as the whole log would (FR-199). Both are optional and additive within format 1, and no format number moves: a build that predates them ignores them, and this build opens a checkpoint without them failing closed, judging an id it cannot place that begins with a kind the app declares as a removed record of that kind. A host that keeps the archive mends such a checkpoint by taking it again at the same seq from the archive — `archiveFrom(store, archive, store.log.horizon)` on `@graview/core/seat`, which reads the archive from seq 0 or from an epoch it begins at that keeps `removed` (FR-214). A build that predates them and compacts again writes its next checkpoint without them, and a store that never knew every record it held (it was opened on such a checkpoint) writes no `removed`, rather than claim to. They are never served to a seat.
- An archive may begin at an epoch rather than seq 0 (FR-214): a host that keeps a plan's window of history makes the epoch where the window begins (`archiveFrom`, with `creators`, `removed` and `writers` like a checkpoint), deletes what lies behind it and keeps the one epoch. `archivedSeenBy`, a full export and a mended checkpoint read from it; a range behind it is answered with `keptFrom`, its seq. An export bundle that begins past seq 0 carries the epoch it begins at as `checkpoint` (additive to bundle version 1), so it restores as a compacted store opened on it; a bundle without it is the whole history from seq 0, or, from a build before it, a tail that does not restore alone.
- A snapshot file — a seed, a projection a product emits, what `graview serve --seed` and `graview sync-seed --seed` read — is `@graview/core/snapshot`'s line format, `"format": 2` in its header line: when it was made (`generatedAt`), records per kind, links per kind and where each kind's lines are, then one record per line, each kind's together, then the links. A header key may be added when it is optional; anything a reader needs to find a kind's lines moves the format, and `readSnapshot` refuses a newer one by its number. An old `{ nodes, edges }` file is format 1 and reads on every build of the major (`readSnapshot`, `fetchSnapshot`, `--seed`). What an adapter stores (`snapshot.json`, a browser's `localStorage`) is not this file and is unchanged.

##### One writer per log, and a sync state's format (1.0)

- **One writer, enforced.** A scope's log has one writer. `PersistenceAdapter.appendOps(scope, ops, { head })` takes the seq the first op appended takes, as the writer last knew the log; an adapter that holds its log elsewhere throws `LogHeadMovedError` (`scope`, `expected`, `found`) and appends nothing — compare-and-set — so two writers fail loudly rather than interleave two histories under the same seqs. The memory, SQL and SQLite adapters compare and append in one transaction; the file adapter reads its head from the log's last line and the browser adapter from storage, at each append, so another process or tab is seen, though not one that writes between the read and the append. `openStore` always passes the head, and reports a refusal through `onPersistError` and writes nothing after it; a journal another tab's write left behind is reported and not put back, and the store opens on what is stored. `head` is optional, and an adapter written before it still works; one that ignores it gives up the check, not the store.
- **A sync state carries its format.** A host keeps a `SyncState` between runs, so it is a stored format: `SyncEngine.snapshot` and a run's `state` are stamped `format: SYNC_STATE_FORMAT` (1), a state without a stamp is format 1, and an engine handed a state in a newer format refuses it with `NewerFormatError` (`what: "sync state"`) rather than run on links it would misread.

- **A sync state may say what a connection last did** (Roadmap f-sync-guest-changes-in-history), still format 1: `guests`, by record, the addresses its last write that reached the calendar said (`sent: { addresses, notified, at }`) and the last write with guests that did not go (`refused: { addresses, error, at }`), and `lastPass` (`{ at, offline, problem?, applied, pushed, queued, conflicts, refused, invited, removed }`). Both are read back by pure functions on `@graview/core/sync` — `guestsOf(state, declaration, localId)` (what was sent, quiet or mailed, the attendee addresses both sides last agreed and those matching nobody here) and `connectionStatus(state, declaration)` — and a build that predates them drops them. A `SyncReport` may carry `guests`: per record, the addresses a write that reached the calendar invited and took off, and the people it reaches and left out (`leftOut`, each `{ person?, address?, why: "invite-off" | "no-address" | "not-a-person" }`); a refused or held write invites nobody.

#### 3. The wire and live protocols: additive within a major

`WIRE` (in `@graview/ship`) lists every route `serveStore` answers, and `createStoreHandler` answers the same routes in any runtime (FR-09). `WIRE_PROTOCOL` numbers the protocol. The guest-view protocol (`@graview/guest`, FR-04) is held to the same rules, and `GUEST_PROTOCOL` numbers it.

- Within a major, a route or a response field may be added. None is removed, renamed or changed in meaning.
- A request field the server does not know is ignored, never refused.
- A `call` or an `undo`, on the socket and over `POST /graview/ops`, may carry `lineage` (FR-172), and a lineage may name the suggestion a change accepts (`lineage.suggestion`), so accepting and declining a suggestion travel as a `call` and an `undo` with nothing new on the wire; the store checks it, a change whose lineage is not one is refused as `invalid` with nothing kept, and the ops every client is sent carry it. `openRemote` sends the lineage a call or an undo was applied with, and again when it sends a change again. A server that predates it ignores the field and keeps no lineage, so a host reads `capabilities().shipped` for FR-172 before it relies on one.
- A host's model is a seam on the page, `HostAi.complete: Completion` (`@graview/tools`), settled for 1.0 in 0.1.49: it is asked with one object, `{ prompt, system?, images?, signal? }` (`images` each `{ mediaType, data }`, base64), and answers `{ text, usage? }` (`usage` `{ inputTokens, outputTokens, costUsd? }`). Within a major a request field may be added when it is optional, and a model that does not read it answers as before; a reply field may be added the same way. The dev server's door (`AI_BRIDGE_PATH`, `aiDevProxy`) takes the same request less `signal` as its POST body and answers `{ text, usage? }` or `{ error }`. Before 0.1.49 a completion was `(prompt: string) => Promise<string>`.
- The live socket at `/graview/live` (FR-05) holds to the same rules: a message type or a field may be added, and a message the server does not know is ignored. `hello` and `welcome` carry `WIRE_PROTOCOL`, so either side can tell what the other speaks. Its positions are cursors, as `/graview/since?seq=` takes them (below, *A cursor is opaque*).
- A refusal's `reason` (FR-46) is one of `REFUSAL_REASONS` — `forbidden`, `missing`, `invalid`, `limit`, `unavailable`, `refused`, `unauthenticated`, `quota` — on the socket's `refused`, on every refusing answer of the routes and on an agent tool's refused answer. A code never changes meaning. A code may be added within a major, and the changelog says so as a change to this surface; a client meeting a code it does not know treats it as a final refusal (below, *Refusal codes are open*). `refused` (FR-119) is an act's own rule saying no to a well-formed call — a document act's `allowedWhen`, a TypeScript mutation's `ActRefusal`, whose reason is `refused` unless it names another; `invalid` is the call as sent — its arguments, one the act does not take (FR-121), a call that changes nothing. A client that predates `refused` treats it as it treats any code but `unavailable`: final, the change taken back. `wouldNeed` is the roles that could, when the policy knows them. A call naming a record the seat may not see is refused exactly as one naming a record that does not exist — `missing`, one sentence that names the act and not the id (FR-55) — and permission is asked of it as if the record were not there, so no refusal tells a guessed id from a real one. An act runs under its caller's sight (FR-55): its body, its condition, its refusal and its sentence read the store as the caller is served it, so a record the caller may not see is to the act what one that does not exist is — whether it runs, what it refuses with and why, what it writes and what problems it answers with are the same for a hidden record as for an absent one, and the page that guessed the outcome from the seat's view is confirmed by the host rather than refused after it. What it writes lands on the whole store, and the store's own bookkeeping reads the whole store — a removed record's links, a patch's prior values, a single source's other links, an id already taken — without telling the seat (FR-55). Ids are unique across the store, so a seat that may not see every record may not ask for the id of one it makes: it is refused alike (`invalid`, "… makes its own id here") whether a hidden record holds that id or nothing does. An id minted from a label for a kind the seat may not see every record of is the seat's own — `room:green.<mark>`, where the mark is `seatMark(<the seat's id>)`: seven letters and digits, the same for the seat on any store, which no other seat's label mints and which does not spell who the seat is, since every seat that sees the record reads its id — stepping only past what it sees, and one that would land on a hidden record anyway (an id somebody asked for) takes a suffix no guess collides with; a seat that sees every record of the kind gets `room:green`, `room:green-2` as before. An act that sets a single-source link and takes a hidden record's link with it is served to the seat whole, with what it may see — the link it took is no part of its op — and the seat may undo it, which puts that link back. A rule that must hold across what a seat may not see — no double booking — is an invariant's, not an act's. `graview check` warns of each act that reads a kind some role allowed to run it may not see (`act-reads-hidden-kind`, FR-105), reading a document's act for itself and a TypeScript act by the kinds it declares it `reads`: run by that role, it judges as though there were none. A seat's problems are judged over what it sees, facts and lines included, wherever it reads them — `seenBy(…).violations()`, a seat's tools, a page served only what its seat sees — so a rule that counts records the seat may not see says the count it sees, and a record it may not see never makes, mends or words one of its problems. An act's answer to a seat (`answerSeenBy`) gives what the act broke, what it mended and what stands after it — a change made or a preview — as the seat judges them over its own world: what it is served, and that world with the change as it is served taken back, or for a preview put on. So whether a rule that reads beyond its subject (a fact, a sweep, a relation) was broken or mended is the seat's own answer, in its own words, and never the whole graph's; the judging is `@graview/core/lines`', which a seat's tools load, and without it an answer to a seat says no problems at all. A fact in a rule's line is said by its `label`, or its name in words. `graview check` warns of each rule whose message says a fact over a kind some role told of it may not see in full (`rule-says-hidden-fact`). A rule is judged on every change and once on load; one that reads the clock — `today()`, `now()`, a computed field that does, a kind whose records retire on a date — is judged again on the day a host ticks the store to (`store.tick(now)`, FR-176), which answers `{ day, was?, appeared, cleared }` and tells every subscriber with an empty diff and no ops, logging nothing. `@graview/ship`'s `openStore` and `openRemote` tick just after each midnight by the clock `today()` reads (UTC) until `close()` (`openStore`'s `tick: false` leaves it to the host); a host that sleeps through timers ticks from its own alarm. A tick holds for the rest of the day the clock read when it was made: once the clock's day moves past it, the store judges on the clock again until it is ticked, so a timer that slept through midnight never leaves a store on yesterday. `clockReaders(schema, rules)` on `@graview/core/check` says which rules and computed fields read the clock, and `graview check` notes them (`rules-read-the-clock`). A store pinned to a day (`invariantOptions.today`) stays on it.
- `busy` (FR-45) is not a refusal: the host asked for the change again after `retryAfter` milliseconds (429 with `Retry-After` over HTTP), nothing was judged, and a client keeps the change. `limit` is a refusal: the change can never succeed as asked, and is taken back. `unavailable` is the one refusal that is not final: the host takes no changes for a while and cannot say how long (503 over HTTP), nothing was judged, and a client keeps the change and sends it again, backing off. A call sent again after it landed is answered with its ops before a host's `limit` is asked, so it is never told busy, `limit` or `unavailable`.
- Op format 2 travels as an addition to protocol 1 (0.1.43). A reader says it reads it — `hello.opFormat`, `?opFormat=2` on `GET /graview/state` and `GET /graview/since`, `opFormat` in the body of `POST /graview/ops`, `WireAsked.opFormat` for a host that routes its own requests (`opFormatOf(url)` reads the query) — and is sent ops bare. A reader that says nothing, as every client before 0.1.43, is sent each op with its inverse written out (`opsFor`), as format 1 had it, so an older tab goes on undoing and playing back against a newer server; it costs that tab the bytes format 1 did. A newer client against an older server is sent format 1, which it reads. `WIRE_PROTOCOL` and the subprotocol do not move.
- A presence may say where somebody's caret stands in a field typed together (collaborative text, phase 4): `caret: { node, field, anchor, head, rev }`, offsets in UTF-16 code units against the text their log held at `rev` ops, which a reader carries over the splices its own log took since by anybody else. A server keeps it only when it is a record, a field and three counts, and withholds it from a seat whose sight keeps that record or that field from it; a reader that does not know it ignores it.
- Op format 3 (`splice-text`, collaborative text) travels the same way. A reader that said `opFormat` 3 or more is sent each splice as it is kept; one that said less, or nothing, is sent the same change as a `patch-node` of the field's whole text before and after it (`opsFor(opFormat, ops, store)`) — at a broadcast from the text as the splice left it, in a catch-up and a welcome by walking back from the text now — so its copy folds to the same text. A reader served behind the head is sent splices only through the seq it is served, the same way. A keystroke is the `type-text` call; `rev` on it is where its sender last read the log, and one behind the horizon is answered as a stale write (`conflict`, with `theirs` the text now and `saw` the `rev`), since the history it would be carried over is gone; a host's compaction keeps the horizon behind every open socket (`protocol.floor(peers)`, `handler.pins()`, the adapter handler's `compact`). A field typed together is never compared as stale: a call's `base` names it so a whole write over it merges three ways with what was typed since (`ApplyOptions.base`).
- A field's revision, which a stale write is refused against, is the seq of the op that last wrote it. It is derived from the log and never stored, so it never changes a stored format.
- `WIRE_PROTOCOL` moves only when a client of the previous protocol can no longer be served, and that is a major.
- A host that stops serving an older protocol says so with `reload` (FR-44): `minProtocol` names the lowest it serves, and a client carries its unsent calls across the reload. `hello.wire` and the subprotocol `graview.ship.1` name ship's codec, so a host can serve another beside it on one path. `build` in `hello` and `welcome` is the host's opaque string and is never judged. A host numbers its own half of the wire with `hello.hostProtocol`, which `minHostProtocol` answers with `reload` carrying `hostProtocol`; `hello.protocol` stays `WIRE_PROTOCOL`.
- A client names its batch as a `Store` mints it, `batch:<tag>:<n>` or `undo:<tag>:<n>` (`isClientBatch`); any other is refused `invalid`. A batch sent again is answered only with the asking seat's own ops, and one that holds somebody else's is refused `invalid`. A server mints its own batches outside that shape (`served:…`), and serves another seat's withheld op under an opaque `withheld:<16 hex>` batch. A `via` in a call or a post is a claim, ignored unless the host's `viaOf` accepts it (FR-52).
- The declaration `version` a welcome, a route and a `declaration` push say is the host's own monotonic number for the declaration it serves, the one a client hands `resolveApp`; a push with the number a client already serves is ignored.
- A declaration change is pushed as `declaration` (FR-43), and every welcome says the declaration `version` it serves. Neither moves `WIRE_PROTOCOL`.
- A host that holds the app read-only says so (FR-66): `{ t: "held", sentence }` to every socket that said hello when the hold starts, `sentence: null` when it ends, `held` in every welcome and on every answer a poll reads while it stands, and every change meanwhile refused `unavailable` in that sentence. Additive to protocol 1, so it does not move `WIRE_PROTOCOL` or the codec's name: a client that does not know the message ignores it.
- What a seat is served holds no id of a record it may not see (FR-55): not in the snapshot, the log, an op's primitives, inverse, reads, writes, call or sentence, a presence, a conflict, `/graview/health` or a tool's answer — beyond the seat's own words. A field whose current value this seat wrote (or the person an agent acts for; an undo is never the author of what it puts back) is served as written, whatever it names, and a record withheld only for such a field is served; so is the seat's own call in its own ops, and an argument it sent that an answer says back. A seat that guessed an id and wrote it is then served the same whether the guess was real, and a write of the value a field already holds, when that value names what the seat may not see, is kept in the log as the seat's. An oracle that checks what a seat is served excludes the strings the seat itself wrote. An act's sentence is worded from its author's view: `describe` reads the graph as the author is served it, so a record the author may not see is named only by what the author wrote, as one that does not exist is — and a reader who sees more reads that sentence as the author would have. The seat's own words excuse only what it wrote — values in its primitives and the inverse that puts them back, and its own calls; another author's call, sentence and name are judged by sight alone. An op records which records its sentence read (`described`), and another author's op is served whole only when its reader may see every one of them. An answer's `reads` name only records the seat sees; an id that names no record is left out as a hidden one is. `seatLens` is the judgment, and `seenBy`, `logSeenBy`, the routes, the live socket and the agent tools all read it. A seen record whose field names a hidden one is served with that field cleared when its kind declares the field optional (or does not declare it); when the field is required, clearing it would serve a record that fails its own declaration, so the record is withheld from that seat whole, as if its sight did not reach it — with its links, and with every op that touched it withheld. An op whose only mention of a hidden record is in its `reads` or `writes`, and whose primitives are served as written, is served whole with those trimmed. A link the seat is not served is no part of an op that did anything else: it is left out of the op's primitives and of its inverse, and the op is judged without it — so a removal that takes a record's links to what the seat may not see is served to the seat whole, as it would be had there been no such link, and the seat may undo it (the undo puts the links back, and is served to the seat the same way). An op that did nothing but such links is withheld. Any other op that names a hidden id is withheld, and its primitives are judged by whether each record was served just before and just after them: served to served is the patch as the seat is served the record (a hidden id written into an optional field arrives as that field cleared, `UNSET`); not served to served is an `add-node` of the record as now served, with its links to records the seat is served; served to not served is a `remove-node`; neither is nothing; and a link is served when both its ends are — an end that is not there at its moment, as a dangling link a repair removes has, is judged as `seesId` judges its id, so one that names no record is served and one that names a record the seat may not see, removed before, after or with the link, is not (FR-67). A seat from whom nothing is kept (`hidesFrom` false) is served every op as it is. So the log a seat is served folds — from nothing, from any cursor, or from the epoch base its view serves after a compaction — to exactly the snapshot it is served. `/graview/health` keeps `ok` and every count the whole store's — a poller asks whether the store is well, a count names no record, and a count of only what the asker sees would call a broken store well — and its `danglingEdges` names only the links whose ends the asking seat may be told of; a caller the host cannot tell is judged as a seat with no id and no roles. This narrows what a seat is sent and never adds a field, so it does not move `WIRE_PROTOCOL`.
- A sight may keep fields as well as records (Roadmap f-field-sight): `policy.sees[].hide` (field names it keeps) and `policy.sees[].fields` (the only field names it shows), both optional. A field of a record is shown to a seat when ANY sight that shows the seat that record shows the field — sights add up, `own` and `via` judged as for the record — so a sight with neither key shows every field. A field kept from a seat is never in anything it is served: the record (cleared, or the record withheld whole when its kind requires the field, as for a required reference), its log (an op that adds or removes a record with a kept field, writes one, or whose sentence read one is withheld whole whatever the field held, its primitives served as the seat is served the record; its own ops are served as it wrote them), an answer's diff and primitives, a conflict (a revision of a kept field is not compared or said), a search hit, a name a call resolves (a label is worked out from the served record), a form, an edit offered in place, a static page, a computed field (worked out over the served record) and a rule (judged over what the seat is served, so a kept field reads as none) — and nothing a seat reads differs between a kept field that holds a value and one that holds none. A seat may not write a field kept from it: an act that would is refused `invalid` as an argument it does not take ("does not take "phone"; it takes …"), asked before a write of the value the field holds is let go as no change, so the refusal is the same whatever it held and whatever was written; a kept field an act leaves unset is no write. An import refuses a column that goes to a kept field exactly as one that goes to no field. An op's `described` may name `<id>#<field>` for each field of a record of a kind some sight keeps fields of that its sentence read. Judging fields is `@graview/core/field-sight`'s; until it is loaded, a sight with `hide` or `fields` shows nothing — the store keeps the record rather than serve a field it cannot judge, and says the seat neither sees every record of the kind nor, when it may begin none, the kind at all (`kindsKeptFrom`) — except in a store `openRemote` opened, which shows what its host served it: that store alone (`FIELD_SIGHT.served`), never another store the same page holds whole. An agent's tool for an act leaves out each argument that writes a field no sight granting the seat that kind shows on any record (`argumentsNeverShown`, `@graview/core/json-schema`), so the tool names no field the seat may not see, and `toolDefinitions` says the same surface without a store. `@graview/ship`'s server entry loads it; a page that holds its whole store (`openStore` from `@graview/ship/browser`, or a `Store` of its own) imports it, as does a host that serves seats without `@graview/ship`. A build before 0.1.29 ignores both keys and shows the field: a host serves a declaration that says either only on a build that exports `FIELD_SIGHT` from `@graview/core`.
- An act may touch what its seat cannot see (FR-55), and `replaces` (FR-115) is such an act by design. Before it connects, it severs the subject's links of the relations it names, all but the one it makes — whatever record is on the far end, seen or not — exactly as connecting a cardinality-one relation severs the link it displaces. A seat that moves a component to a new owner may so cut its link to an owner it may not see. That is the policy, not a leak: the seat is served the severed link as nothing (a link is served only when both its ends are), the op as its primitives are judged above, and an agent tool's answer the same way, so the act changes what the seat cannot see without telling it what was there. An installation that must not let a seat displace a hidden record says so in the act's condition or its grants, not by relying on sight.
- A status board's moves (FR-108) are judged against the graph the page holds, and the host judges them under the seat's sight. On a served app the page holds the seat's view, so a named step whose condition reads a record the seat may not see is judged without it on the page and at the host alike: a step is offered exactly when the host would run it, and run when offered. Nothing tells the seat what it cannot see, and nothing moves `WIRE_PROTOCOL`.
- A host's files (FR-163) are a seam on the page, `files: { upload(file, name), maxBytes, kinds }` on `mount`, `<Embed>`, `GraviewProvider`, the Shell and the routed face's context, and the route that serves them is the host's own; within a major the seam's three members keep their meaning, and the value `upload` answers is a `FileValue` (FR-162) the record keeps as it is. What the route serves is part of the app's origin, and the page draws it as such: a picture in an `<img>`, which never runs a script, an SVG's included; a PDF in an `<object>`, which draws whatever type the route answers with; anything else as a link with `download`. So a host's files route: serves each file as the type the host decided from its bytes, never the type the uploader said, with `X-Content-Type-Options: nosniff`; sends `Content-Security-Policy: sandbox` with everything but a PDF (an SVG or an HTML file opened from it, in a tab or in that `<object>`, runs as the app otherwise), and with a PDF where its readers' browsers draw one sandboxed; says `Content-Disposition: attachment` for anything that is not a picture, a PDF or plain text; and serves a file only to a seat that sees a record holding it, the framework's sight being per record (`seesId(store, principal)` over the records whose fields hold the `href`, by `filesOf`). The dev door (`devFiles`, `@graview/ship/dev`) does the rest but the first and the last: it keeps the type it was sent, which under `nosniff` and the sandbox runs nothing, and every seat on a dev server is its one person. A host's page that carries a `Content-Security-Policy` allows the files route in `object-src` (`'self'`, or the files origin) if it wants a PDF drawn inline; where it does not, or where the browser draws no PDF (an iPhone), the page draws the PDF's one line — its name, its type, its size, Open and Download — and the `<object>` takes its height only once the browser has loaded the PDF into it, so nothing is lost and no empty box is drawn (FR-234).
- A host's way to name another app (FR-171) is a seam on the page, `resolveApp(address, viewer)` on `mount`, `<Embed>`, `GraviewProvider`, the `Shell` (asked before the provider's) and the routed face's context, answering `{ name, icon?, headline?, href }`, `{ denied: true }` or `null`; within a major those three answers keep their meaning. The page asks once per address and viewer and remembers the answer for as long as it holds that resolver; a throw is taken as `null`. A viewer the host refuses is shown "linked app (no access)" and nothing the host did not answer, so whether another app exists, what it is called and what its home says stay the host's to tell each viewer. Without a resolver the address is drawn as it is kept, a link only when it is an absolute http(s) address, opened apart from the app (`rel="noopener noreferrer"`). `href` is followed only when it is a path on the host or an http(s) address.
- A host's way to read another app's records (FR-171) is a seam beside it, `linkedRecords: LinkedRecords` on `mount`, `<Embed>`, `GraviewProvider` and the routed face's context: `resolve(ref, viewer)` with `ref` `{ address, kind, id }`, answering `{ address, kind, id, label, describe?, card?, fields, href?, app? }` (`fields` only what that viewer may see there), `{ denied: true }`, or `null`; `find({ address, kinds, query, limit }, viewer)`, answering the records that viewer may link or `{ denied: true }`; and `open(ref, viewer)`, optional, the navigation seam a press on a linked record calls in place of following its `href`. Within a major those answers keep their meaning. A page asks once per record and viewer; a throw is `null`. A viewer refused is shown "linked record (no access)" and nothing the host did not answer. `href` is followed only when it is a path on the host or an http(s) address. `linkedRecordsOver` (`@graview/core/linked`) is that seam over stores a host holds in memory, each record read through the far store's `seenBy(viewer)`; `recordLinkedChange(store, { ref, fields, app?, at? })` keeps a far change in the reading store's history as an ordinary op — author `{ kind: "system", id: "app:<address>", name }`, `via: "app:<address>"`, `reads` the linking records, no primitives, no new op field, naming the fields that changed and none of their values.
- A worker view's manifest and what it is handed are held to the guest protocol's rules: a key may be added when it is optional and a manifest without it means what it meant; a build that predates a key passes it over (one before 0.1.18 draws a view with `replaces` as it drew every view of one: alone). `replaces` arrived this way (FR-149): `"page"` on a view of one record draws it alone in place of the record's own fields, and `checkManifest` refuses any other value and the key on a view of the home. Since FR-203 a view of many may say it too, and is then drawn on its kind's list page (`/<plural>`) in place of the list, a titled one at its own place as well; before, `checkManifest` refused it there, so no manifest that worked reads differently, and an earlier build refuses it. What a view of one record replaces changed without the manifest's text: since FR-149 a view of one is drawn above the record's own editable fields on the scene (on Pages it always was), where it was drawn alone; a host that relied on the record being the view alone adds `replaces: "page"`. `data-prefill` (FR-150) is an attribute a view draws, judged by the host: it fills only an empty `input` or `textarea` whose `name` is the field, from a record the view was shown, read through the viewer's sight, when an act in its `fieldset` named in the manifest writes that field of that record and the viewer may run it there; a press carries the value only back into that field, and any other press carrying it is refused `untyped`. A view's props are as they were: each record's fields on it by name, beside `id`, `kind` and `label` (FR-151 corrected the guide, not the props). `GUEST_PROTOCOL` does not move.
- What a view may name in `data-place` and `graview.navigate` is one vocabulary since FR-235 — `placeNamesOf(app)` and `placeNamesFrom(schema, places)` on `@graview/core/navigate`: `overview` (the Scene), `home`, each kind's list by its slug and each titled place by its slug, less what the viewer is kept from — and the headless check and the live host read the same list, so a name the check passes the page follows. A view's `props.places` lists that vocabulary (`{ as, title, kind }` each, the Scene's and the home's `kind` empty) on the page as a headless run handed `placesOf` already did; a view that read only titled places from it reads the same entries among more. A version may add a name to the vocabulary and says so in the changelog; it never takes `overview`, `home`, a list's slug or a place's slug away.

##### Refusal codes are open (1.0)

- A code may be added within a major; none is removed or changes meaning. A client that meets a code it does not know treats it as a final refusal: the change is taken back and the refusal handed on with the code as it came (`openRemote`'s `onRefusal`, `RemoteRefusedError`), never kept and sent again as `unavailable` is. A program that branches on codes keeps a default for the rest.
- `unauthenticated` (1.0's foundation): the host does not know who is asking — no session, or one that ran out — and signing in again may let the same change through. 401 over HTTP.
- `quota` (1.0's foundation): the account the app belongs to has used what its plan allows; the change may succeed once the allowance grows, never by waiting. 403 over HTTP.
- A host says either, and `limit`, as its own final refusal: its `limit` or `admit` answers `{ refuse, reason }` (`HostRefusalReason`; `limit`, 413, when it names none). A body too large to take is `limit`; a caller sending too much too fast is told `busy` with a wait, which is not a refusal. Neither needed a code of its own.

##### Served state and the head

What a seat is served is the app as this seat is served it, and nothing on any surface promises that is the store's head. FR-55 narrows what a seat is served by record and by field; a seat's served state may also end before the head, at a seq a policy chooses, and that is narrowing by seq — the same kind of change, not a break — so it moves neither `WIRE_PROTOCOL` nor any format.

- A seat is served through a seq, `servedSeq`: the ops before it are in what it reads, none after. `Store.servedSeq` says it, read-only: a store's own is its head (`log.length`), a past's (`pastOf(store, seq)`) is `seq`, and a seat's view (`seenBy`) is the seq that seat is served through. Every seat of a live app is served through the head; a reader of an app that publishes is served through the last publish (below).
- `GET /graview/since?seq=<cursor>` answers the ops after the cursor that the asking seat is served — through its served seq, which is the head unless a policy holds it behind — not necessarily every op to the head, and the cursor where they leave it. The live socket's positions mean the same: `welcome.seq` is where the seat stands in what it is served, and `ops` brings what the seat is served as it lands. A client that takes a position for the head's takes it for the seat's (below, *A cursor is opaque*).
- `seenBy`, `Store.seenBy`, a provider's `store`, `useGraph`, an agent's reads and a seat's model prompt read the app as the seat is served it. Their doc comments say so and promise neither the head nor one view object per principal: the view is kept only to save judging again, keyed by everything serving reads (the seat's kind, the id and roles it is judged as, the agent's own id when it acts for somebody — two agents for one person are two seats — and where it is served through).
- A write is always judged at the head, whatever the seat is served. A call's stale-write check (`base`, FR-05) reads the head's revisions: a seat served behind the head that claims the revision it read is not stale unless the field was written after that revision, and when it was, the conflict says the head's value.
- A client whose seq the ops cannot catch up is sent the whole state, never the ops after a gap: a socket's `hello` whose seq is behind the compaction horizon, or past where its seat is now served, is answered with a `welcome` carrying `state` (and such a `welcome` may come unasked when a publish is taken back); `/graview/since` answers such a seq with `reset: true` — and, behind the horizon, the ops after it, so a client that predates `reset` still sees the gap. `openRemote` takes the state on either.
- A checkpoint never passes a seq somebody is served at. `CompactOptions.pins` (`store.checkpoint`, ship's `opened.compact`) are such seqs, and the horizon stops at the lowest, so `pastOf(store, pin)` still folds from the log. A host that serves a seat behind the head passes that seq.
- **Publishing** (Roadmap f-publishing-lifecycle). A declaration's `publishing` (`{ mode: "live" | "on-publish", working: [roles], publishers?: [roles] }`, the document's key and `defineApp`'s alike, `StoreOptions.publishing` on the store) says when edits reach readers. `"live"`, or absent, is every app as it was. Under `"on-publish"` a seat whose roles (an agent's read through the person it acts for) are `working` is served the head, and every other seat — a visitor, an embed, a static page, another app's linked read, a describe for a reader — is served `pastOf(store, publishedSeq)` as its sight reaches it; before the first publish, the log's start (the seed, or the horizon of a log compacted past it). `seenBy(principal, { as: "published" })`, a provider's `as` and `?as=published` serve a collaborator what readers are served, to preview it. Writes land on the head whoever makes them: a visitor's form answer is in the working state, and reaches readers with the next publish. A publish is the built-in act `publish` (`{ through? }`), offered to `publishers` (absent, `working`): one op authored by the person who published, with no primitives and the op field `publishedThrough` — the seq readers are served through, its own seq + 1 unless `through` names an earlier one. The last publish op that stands says it (`Store.publishedSeq`), so taking a publish back is an undo of it, permitted to publishers. How a reader is served, the `publish` act and the published seq are `@graview/core/publishing`'s, an entry of its own so a live app's page carries none of it: a server, a static page, a linked read and the agent tools load it, a page fetches it with `@graview/core/past` before it draws an app that publishes, and until it is loaded a reader of such an app is refused — never served the head. A checkpoint keeps the app as it stood at each published seq behind it that readers are or may again be served (`Epoch.published`, a list of epochs; also `Epoch.publishedThrough`, what stood published at its seq), so a compaction passes old publishes, a reader is served one behind the horizon from it, and only before the first publish is the horizon held, at where the log begins. Both are optional and additive within format 1: a checkpoint without `published` serves readers what the log folds and refuses an undo of a publish that would send them behind the horizon. A store whose checkpoint carries `published` is snapshot format 2 (§2), so a build that predates `published` refuses it rather than serve its readers the horizon; a host that must roll back to such a build compacts with `format: 1`, which holds the horizon at the earliest seq readers are served behind it and says where it stopped (a pin at `store.publishedSeq` alone does not: a horizon between two publishes is format 2 with it). Neither is served to a seat. On the wire, a reader's `welcome`, `/graview/state` and `/graview/since` carry `servedThrough`, a cursor as opaque as any other position (below, *A cursor is opaque*), absent in a live app, its socket is sent the ops between two publishes when the second lands, and the whole state when a publish is taken back. A build that predates publishing folds an op carrying `publishedThrough` as it would without it (a marker that touches nothing) and refuses the document key by path (§4) — the fail-closed way back: an app that publishes is never opened by a build that would serve its readers the head. Named by no FR id yet: `capabilities().shipped` gains one when Graview Cloud files it.

##### A cursor is opaque (1.0)

Where a reader stands in a log is said on the wire as a cursor: a string only the server that gave it reads, meaningful to no other server and to no other store on the same one. A store keeps numbering its ops, and an op's own `seq` is unchanged; what moved is every position a client and a server say to each other, so a server that one day merges several writers' logs can say where a reader stands without one sequence.

- **Where it is said.** `GET /graview/since?seq=<cursor>` takes one and answers `cursor`, where its ops leave the reader; `GET /graview/state` answers `cursor`; `POST /graview/here` takes `seq` and answers `cursor` beside its ops; the socket's `hello` says `seq`, and its `welcome`, `ack` and `ops` say `seq` (`Cursor`, `@graview/ship`).
- **What a client may do with it.** Keep the last one it was given and send it back. It must not read one, build one from an op's `seq`, or compare two. `openRemote` speaks the same build's codec as the server it was built with (`cursorAt`), and a cursor today is `s` and a count in base 36 — which is this build's business, not a promise: a server may change what is inside within a major.
- **A page from before it** (0.1.48 and earlier) sends the seq of the last op it has, a number. A server reads that, and a numeric string, as before for one minor (`seqAt`), and stops in the minor after; such a page reads nothing it is sent as a number, so the tokens in a `welcome`, an `ack` and an `ops` message do not disturb it. A seq a server can read as neither is refused `invalid` (400).
- `SyncState.cursor` was a remote system's own string from the start and is held to the same rule: the engine keeps it and hands it back, and never reads it.

#### 4. The declaration, the document format and check finding codes

A declaration that compiled and checked clean on one version compiles on the next version of the major.

- A check finding's `code` never changes meaning. A new code may appear, and a new warning or note is not a break. A new *error* on a declaration that used to pass is a break.
- A code that only ever said again what another code says may be retired, and the changelog says so. `act-without-title` was retired this way: a mutation without a title was reported twice, as that warning and as the error `mutation-untitled`, which names the path and the fix and is the one finding now. A program that matched on the retired code matches on `mutation-untitled`.
- The stored-data finding codes of `validateGraph` (FR-21) hold to the same rule. Each is a record, a link or a rule that no longer fits the declaration, found by id:

| Code | What it says | `repairPlan` | |------|--------------|--------------| | `node-shape` | a record's field does not fit its kind (`detail` names the field) | clear an optional field, coerce a required one to its default, else drop the record with its links | | `kind-unknown` | a record of a kind the declaration no longer has | drop it, with its links | | `edge-dangling` | a link to or from a record that is not there | drop the link | | `edge-disallowed` | a link the declaration does not allow between those kinds | drop the link | | `rule-error` | a rule threw rather than judged (`could-not-judge`; `detail` names the rule) | none: the declaration's to fix | | `rule-budget` | a rule would have read more than its budget (`over-budget`) | none: the declaration's to fix | | `derived-out-of-step` | a record that follows another (`kinds.<kind>.derives`) holds a value other than its source works out (`detail` names the field) | set the field again from its source |

- The declaration document format (FR-01) is versioned like a stored format, and `capabilities().documentFormats` lists what a build parses.
- A key may be added to a document format within its version when it is optional and a document without it means what it meant: `kinds.<kind>.computed` (FR-83) arrived in `graview-document@1` this way. Every key is closed, so a build that predates one refuses a document that uses it as `unknown-key`, by path, and never misreads it. A host that keeps documents for more than one build reads `capabilities().shipped` before it writes the key.
- The app's money arrived the same way (FR-100). Its one home is the brand: `brand.currency` (a three-letter code) and `brand.locale` (a language tag) in a document, `Brand.currency` and `Brand.locale` in a declaration, and a document's `brand` may now carry them without an `accent`. A figure or a field shown as money takes `currency` of its own; one that names none, and a template's `{x | money}`, take the brand's, written by `Intl.NumberFormat` in the brand's locale ("en-US" when it names none). A document without them says a sum as it always did: a figure with a currency in that currency, anything else as a number with no symbol. A figure's and a meter's `label` became a template (FR-99): a label without braces says what it said. The rule language gained `out(S, 'edge')`, `in(S, 'edge')` and `&`, `|` and `-` between sets (FR-101); an expression that parsed before means what it meant, except that a `|` inside brackets within a template's braces, which was a formatter and refused, is now a join. A build that predates them refuses `brand.currency`, `brand.locale`, a field's `currency` and a set operator by path, but draws a templated label as its words and a two-argument walk as "—", so a host reads `capabilities().shipped` for FR-99, FR-100 and FR-101 before it writes them.
- A number's range arrived the same way (FR-114): `min`, `max` and `step` on a `number` or `integer` field (and on an act's declared argument), each optional, a field without them taking any number as before. The edit vocabulary gained `set-range`, and `DocumentDiff` gained `narrowedRanges`. A range is judged by the checker (`default-range`, `field-range`), not by `readDocument`. A build that predates them refuses the keys by path, so a host reads `capabilities().shipped` for FR-114 before it writes them.
- An act's `setsOther` and `replaces` arrived the same way (FR-115), each optional, an act without them doing what it did. One meaning changed with them: an act's `connects` or `severs` shorthand on a subject that is only the far end of the relation (`connects: "owns"` on a component, where `owns` is declared on person) now links from the record it is given to the subject, as the declaration says the relation goes; before, it tried the link the other way round, which the graph refused, so no document that worked reads differently. `effectsOf` may return a `ReplaceEffect` beside the effects a document lists. A host reads `capabilities().shipped` for FR-115 before it writes the keys.
- The rest of the brand arrived the same way (FR-124): `brand.logo` (inline SVG, or a path under `/graview/assets/` or relative to the page; a string, or `{ "src", "alt" }`), `brand.favicon` (the same forms), `brand.typography` (`display`, `body`, `mono`: `system-serif`, `system-sans`, `system-mono`, or a stack of faces every system has and the web fonts on `DOCUMENT_FONTS`), `brand.shape` (`radius` 0–32, `density` 0.75–1.5), `brand.accents` (a hue per kind) and `brand.scheme` (`light`, `dark` or `auto`), each optional and each mapped onto the TypeScript `Brand` (which gains `logoAlt`, `favicon`, `subtitle` and `scheme`). A document's `description` is now said on both faces — the app name's hover on the app bar and the line on the routed face's home (FR-131) — and every document compiles to a brand, so a document without one is called by its own `name` where it was called Graview. The checker judges the new keys (`brand-mark`, `brand-font` errors; `brand-accent` a warning about an accent that does not read as given, FR-126). The edit vocabulary gained `set-name` and `set-description`, and `set-brand` takes every key, `null` clearing one; `DocumentDiff`'s sentences for the name and the description changed words ("The app is now called…"). A build that predates them refuses the keys by path, so a host reads `capabilities().shipped` for FR-124 and FR-125 before it writes them. A compiled app carries the new keys in its `brand` within `graview-compiled@1`: a page that predates them draws the brand it knows.
- A logo for each scheme arrived the same way, in 0.1.42, and was named FR-197 in 0.1.44: `brand.logo` as `{ "light", "dark"?, "alt"?, "darkFallback"?: "invert" }` beside the string and `{ "src", "alt" }`, which mean what they meant. A build before 0.1.42 refuses the object by path (`brand.logo`), so a host stores a document whose logo has `light` only on a build whose `capabilities().shipped` names FR-197 — a build of 0.1.42 or 0.1.43 holds the form but does not say so. `logoOfDocument` on `@graview/core/document` reads any of the three forms into `{ light, dark?, alt?, darkFallback? }`.
- One theme for every view arrived the same way (Roadmap f-app-wide-view-theme): `brand.views` as `{ "css"?, "motion"?: "none" | "fade" }` in a document, `Brand.views` in a declaration — a stylesheet every worker view is drawn with before its own, and a fade between records. The stylesheet is held to the sanitizer and the 64,000 characters a view's own is, by the same code: `@graview/core/css` is where the framework's one CSS sanitizer now lives (`sanitizeStylesheet`, the `CSS_*` tables, `OPEN_MAX_STYLESHEET`), `@graview/guest`'s host draws through it, and `graview check` says what of a brand's sheet the open kit leaves out as a warning, `brand-views-css` (an error when it is too long for a stylesheet at all). `set-brand` takes `views` (`null` clearing it, or either key), and refuses a sheet the page would draw only part of, naming the part. A build that predates it refuses the key by path (`brand.views`), so a host reads `capabilities().shipped` — or tries the key — before it writes one. A compiled app carries `views` in its `brand` within `graview-compiled@1`: a page that predates it draws the brand it knows.
- A compiled app (FR-123) is versioned like a stored format. It is what a host hands its page so the page need not compile: `serializeCompiled(compileDocument(document))`, plain JSON with every template and expression already parsed, which `appFrom` (from `@graview/core/compiled`) builds into the same app `compileDocument` made. It says `"format": "graview-compiled@1"`. `appFrom` refuses another format as `compiled-format`, by name, and parts that do not match their document as `compiled-shape`, and never misreads either; `appFromOrCompile` then compiles the document in the page, so a compiled app cached from another build costs one request, not a broken page. It does the same for one torn on its way (refused `compiled-shape`, never thrown) and for one compiled from another document than the one handed beside it — two documents are the same when their canonical text is (`canonicalize`), so a host hands the document the compiled app was made from, in the current document format. Within a version the format is additive: a key an older page ignores, and a page that lacks it can do without, may be added. Anything a page would need to build the same app moves the version: a new effect, a new kind of argument, a change to what a parsed expression or template part holds. So the rule language's tree (`Expr`) and `TemplatePart` are part of this format, and a parser change that alters them is a format change. A compiled app is a cache of its document, never its source. A host keeps the document, compiles it at its own build, and may drop a compiled app at any time. It is the host's own data, checked for its format and shape and not judged again.
- An app's opening screen arrived the same way (Roadmap f-splash-in-document): `brand.splash` as `{ "style": "plain" | "editorial" | "shader" | "ascii", "image"?, "title"?, "kicker"?, "shader"? }` — the image a mark as the logo takes one, the shader the NAME of one `@graview/pages/splash` ships (`SPLASH_SHADERS`), never code. Three codes judge it where the brand is judged: `brand-splash-image` and `brand-splash-shader` (errors; the latter a warning for a shader named on a style that draws none) and `brand-splash-style` (an edit's, since a document's shape refuses the style first). `set-brand` takes `splash` whole, `null` clearing it, and `DocumentDiff` says "The app opens on an editorial screen while it loads." A build that predates it refuses the key by path (`brand.splash`), so a host stores a document with one only on a build that accepts it. A compiled app does not carry it: the screen is a host's first HTML's, drawn from the document. A shader name added to `SPLASH_SHADERS` (`caustics`, after 0.1.62) arrives the same way: a build that predates it says `brand-splash-shader` of it, so a host names a new shader only on a build that ships it.
- A check finding code added this way (FR-99's `view-braces`, FR-100's `brand-currency` and `brand-locale`, FR-105's `act-reads-hidden-kind`, FR-108's `lens-column-unreached`, FR-114's `default-range` and `field-range`, FR-115's `act-sets-other` and `act-replaces`, FR-124's `brand-mark` and `brand-font`, FR-126's `brand-accent`, FR-132's `pages-overview-taken`, FR-137's `pages-faces-alike`, FR-148's `page-field`, `page-field-twice`, `page-group-twice`, `page-unknown-field` and `page-too-large`, 0.1.24's `rule-says-hidden-fact`, 0.1.60's `typing-act-without-allowed-on`, FR-232's `face-reads-content-beside-the-graph`, which `graview check` says of a project's face modules and no declaration or document ever meets, and 0.1.62's `rule-covers-relation`, said only of a rule's `covers`) is a warning, a note or an error only about what is new: `act-reads-hidden-kind`, `rule-says-hidden-fact`, `typing-act-without-allowed-on`, `face-reads-content-beside-the-graph` and `view-braces` are warnings, `lens-column-unreached` is a note, and the brand, range, other-end, page and coverage codes judge keys a declaration could not hold before. A rule's `require` became optional the same way (Roadmap f-rule-covers-every): a rule says `require` or `covers`, one of them, and a build that predates `covers` refuses it by path (`rules.<rule>.covers`) as a key it does not know, so a host stores a coverage rule only on a build whose `@graview/core/document.schema.json` has it.
- The scene's name arrived the same way (FR-132), and its key was respelled when the scene left the places for the bar's switch (FR-137): `pages.scene` and `pages.pages` (at most 40 characters each, as `pages.overview` was) are what the switch calls the two faces, "Scene" and "Pages" when unsaid, and `arrange-pages` takes `scene` and `pages`. The scene keeps the address `/places/overview` whatever it is called. `pages.overview`, which named the scene's tab in 0.1.15 and 0.1.16, is read as `pages.scene` (a line in `RESPELLED`), so a stored document keeps its word, and `arrange-pages` still reads `overview` as `scene`, so a chat or a tool written before 0.1.17 still renames the scene. `pages-faces-alike` is a warning about a declaration whose two words are the same. `pages-overview-taken` is a warning about a declared place whose address is the scene's; that place keeps its page on the routed face, and the place list does not offer it. A build that predates the keys passes them over.
- Where a declaration opens changed without its text (FR-136): an app with a home view (the document's `views.home`, or a worker view attached to `"home"`) and no other `pages.first` opens on Pages at its home when the host names no face, where it opened on the scene, and `placesOf` marks the home `first`. Under address routing the bare address, naming no face, is the home's whatever face the host names, and the host is told the pages (`onFace`). A host that wants the scene there links to `/places/overview`, or hands a stop. An app without a home view opens as before. That address alone is the overview at altitude (FR-154): a fragment never reaches a server, so the framework writes the overview at altitude without one, and reads `/places/overview` with no fragment, or one that says nothing, as at altitude; a fragment that says where it stands (`#focus=t1`, `#overview=1&focus=…`) is read as it says, and `#overview=1`, written before, still opens it.
- A kind's page arrived the same way (FR-148): `kinds.<kind>.page`, `{ "fields": [...], "groups": [{ "title", "fields" }] }`, each part optional, says which facts a record's page shows first and under which headings; the rest follow in the kind's declared order, under "Details" when there are groups. The declaration's `display.page` is the same choice. The edit vocabulary gained `set-page-fields` (`{ kind, fields, groups? }`; an empty `fields` and no `groups` take the choice away), and the compile and `graview check` refuse a name the kind does not have or one named twice (`page-field`, `page-field-twice`, `page-group-twice` in a document; `page-unknown-field` and `page-field-twice` in TypeScript). A build that predates the key refuses it as `unknown-key`. One reading changed without a key: a record's facts are read in the kind's declared order on every face, in `describePlace` and in `readableFields`, where they were read in the order the record's own keys were written.
- A document's facts and a kind's roles arrived the same way, with no FR id (0.1.22). The document's top-level `computed` names facts of the whole graph, each a rule-language expression or `{ "expr", "label" }`, read as `fact('<name>')` wherever the language is read; a fact that reads another in a circle is refused (`computed-cycle`). `kinds.<kind>.fieldRoles` says which field fills a role a lens binds by name, and the framework reads two: `when` (a date; a list of the kind opens newest first by it, and a timeline or calendar draws the kind there) and `who` (a name; an unchosen glance leads with it and `when`); `graview check` refuses a role naming no field (`field-role-missing-field`) or of the wrong type (`field-role-ill-typed`). A kind may word its own end of a relation several kinds declare, so `edge-name-shared` is no longer reported. A build that predates the keys refuses them by path. These carry no FR id, so `capabilities().shipped` cannot announce them, and `capabilities()` does not list document keys: it is on every page's first load, and the keys a build reads are already published with it, as `@graview/core/document.schema.json` (JSON Schema, one per version). A host that writes a document for more than one build validates it against the schema of the oldest build it serves, or lets `readDocument` there refuse it by path.
- A picture or a document on a record arrived the same way (FR-162): the field types `image` and `file`, and `list` with `of: "image"` or `of: "file"`, in a document; `imageField()` and `fileField()` in a declaration, which `toDocument` writes as those types. The value is a `FileValue`, `{ href, name, type, bytes, width?, height?, caption? }`, its `href` a path on the host under its base (`/graview/files/3f9a….jpg`, or one relative to the page) and never a scheme, another host, a backslash or a path that climbs (`safeFileHref`); a store refuses any other value as it refuses any value that does not fit its field. A view's blocks gained `{ "image": "<field>", "as": "thumb" | "gallery", "label"? }`, judged by the check (`view-image`, an error about a block that could not be written before, and `view-format` for its `as`). `graview types` writes such a field as `FileValue` (or `readonly FileValue[]`). A build that predates them refuses the types and the block by path, so a host reads `capabilities().shipped` for FR-162 before it writes them. A compiled app carries the new field types within `graview-compiled@1`: a page that predates them cannot build such a field, refuses the compiled app as `compiled-shape` and compiles the document, which refuses the type by path. A change that leaves no record holding a file says so: `MigrationPlan.files` lists them, and the plan's words name them; what becomes of their bytes is the host's to decide.
- A link to another app arrived the same way (FR-171): the field type `app-link` in a document, `appLinkField()` in a declaration, which `toDocument` writes as that type. The value is another app's address — `@owner/app`, an id its host knows it by, or an absolute http(s) address, at most 500 characters (`isAppAddress`) — and a store refuses any other value as it refuses any value that does not fit its field. `graview types` writes it as `string`. A build that predates it refuses the type by path, so a host reads `capabilities().shipped` for FR-171 before it writes one; a compiled app carries it within `graview-compiled@1`, and a page that predates it refuses the compiled app as `compiled-shape` and compiles the document, which refuses the type by path. A relation whose `to` is another app's kind is the next line.
- A relation to a kind in another app arrived the same way (FR-171, the full relation): a relation's `to` may name `"@<app address>/<kind>"` — `"@nick/house/house"`, `"@app_kf5eydr9z58jzf/house"`, `"@https://example.com/a/house/house"` — every target one app's kind (`parseLinkedTarget`; the address is the one an app-link holds), and `linkedRecordField("@nick/house/house", { cardinality? })` in a declaration, which `toDocument` writes as that relation. The record that links keeps which far record as a value under the relation's name, `"<kind>:<id>"` (`linkedValue`), or a list of them for `"many"`; the far document is never written. `graview check` refuses a relation that mixes this app's kinds with another's (`linked-mixed`), reaches two apps (`linked-apps`), is no app's kind (`linked-target`), or says `inverse` (`linked-inverse`) or `appendOnly` (`linked-append-only`), a declared act that connects, severs or sets one (`act-linked`), and a rule that walks one with `out()` or `in()` (`rule-linked`); a page that compiles without the checker reads such a relation as no relation. ##### A caller names what it makes (1.0)

Ids stay readable slugs when nobody asks for one. Every act that creates — an app's own in code, a document's, a repeat's — takes an optional `id` beside its own arguments (`takesAnId`), so an offline batch or an agent's chain names its records up front and refers to them before any server answers; `applyAll` applies its calls in order, so a later call of the same batch names the record an earlier one made by that id.

- **Honored exactly, or refused in a sentence.** A free id of 1–200 characters with no space or control character is the id the record gets. One a record holds is refused (`Id "<id>" is already taken`) and the whole change with it, never renamed or suffixed; a malformed one is refused before anything runs; and an act that names its records itself, asked for an id, says so (`did not make a record with id "<id>"`) rather than drop it. The id goes to the first record the act mints (`freshId`), and `ApplyResult.minted` says, by call, the id each call's act minted first.
- **A seat that does not see everything** may ask only for an id of its own — one ending `.<seatMark(me)>`, optionally followed by `-<n>`, as the ids minted for it do — since a refusal of any other id could say a record it may not see holds it.
- **A demand and a hint.** An id a caller asked for — the `id` argument, an agent's chain, an offline batch naming its own records — is a demand: made exactly or refused, as above. An id a client minted on its own for a press it applied first is a hint: `openRemote` sends such a call with `mintedHint` beside its arguments (a field of `MutationCall`, additive on the wire; a server before it ignores it). The store makes the record under the hint when it is free and the seat may ask for it, so the rebase keeps the id and a press after it that names the record names the one the server holds. When somebody took it meanwhile the store mints as ever (`-2`), never refusing, and a later call of the same change that names the hint names the record it made; the rebase then holds the server's id, as it always did. Two people adding "Groceries" at once both land. A press in a later change, sent before the answer, still names the hint. The log keeps each call as the store read it, without the hint.
- The tool schema's `id` argument is unchanged.
- `accept_suggestion` and `decline_suggestion` (0.1.62, Roadmap f-suggestion-votes) answer `voted: "for" | "against"` from a seat the store would refuse the change — the vote kept in place of it, the suggestion still waiting — and `list_suggestions` carries each suggestion's `tally`; no tool is added, and no input schema moves.
- `propose_changes` (0.1.63, Roadmap f-proposals-for-review, `{ calls: { act, args }[], intent? }`, answered with `proposal` and its `intent`) is listed for a seat whose principal — or the person an agent acts for — the policy lets propose an act it may not run, and for no other: a surface whose policy names no `propose` keeps its tools and its hash. `list_suggestions` carries `proposedBy` on a person's proposal.

#### Held to semver from 1.0: the JavaScript APIs

The five surfaces are what stored data, a declaration and a model depend on. From 1.0 the JavaScript a host and a product call is held to semver as well: within a major nothing exported from a package's `exports` entries is removed or renamed, a function's parameters change only by an optional addition, and a type changes only so that what compiled against it still compiles — an interface a host implements (`PersistenceAdapter`, `SubscriptionStore`, `KeptViews`, `RemoteSystem`) gains only optional members, and a union a host reads (`RefusalReason`, `Author["kind"]`) may grow, so a host's `switch` keeps a default. That holds for `Store` and its options, `openStore`, `openRemote`, `createStoreHandler`, `serveStore`, the persistence adapters, `SyncEngine`, the React hooks and providers of `@graview/react`, and the declaration's `define*` functions. What a page draws — the React components of `@graview/primitives`, `@graview/pages` and `@graview/embed`, and their DOM — is the look (below) except where this page names a marker a host reaches. A module a package does not list in `exports`, and anything named internal, is not held.

The files that count as each of the five surfaces for the `Compatibility:` line are listed in `scripts/lib/surfaces.mjs`, which since 1.0's foundation also names the sync engine and its state (`packages/core/src/sync/`), subscriptions and their stored file (`/graview/subscriptions`, `subscriptions.ts`, `file-subscriptions.ts`), a host's views and their file (`views.ts`, `remote-views.ts`, `file-views.ts`), presence (`packages/ship/src/presence.ts`) and the refusal codes (`refused.ts`).

#### Not a surface: the look

The values the theme writes — the shipped palettes, the default faces, weights, radius and spacing, the kit's defaults — are not one of the five, and a patch may move them; the custom properties' names, the `Brand` keys and what each means are kept, and a change to a value is said on the changeset's `Compatibility:` line. A host that wants its look held still declares its own brand (`schemes`, `typography`, `shape`), which the framework never overrides.

How a notice looks is the look too (FR-75, FR-236): a toast or a banner is one hairline all round in the app's radius, its tone a small tinted chip at its head (`[data-testid="notice-chip"]`, hidden from a reader, who is told the tone by the status or alert the notice is announced through) and never a colored border on one side; the sentence is `[data-testid="notice-sentence"]`. What a host's page or harness reaches is kept and said on the `Compatibility:` line when it moves: the card `[data-testid="notice"]` with its `data-kind` and `data-tone`, its acts `[data-testid="notice-action"]`, its `[data-testid="notice-dismiss"]`, and — on a warning or error toast the framework raised itself, when the host gave `onReport` (FR-237) — a native `[data-testid="notice-report"]` whose accessible name is `Report this: <the toast's first sentence>`, which hands the host `{ message, code?, place?, record?, version }` and leaves the toast standing. The hook's shape is a JavaScript API (`NoticeReport`, on `mount`, `<Embed>`, `@graview/embed/pages` and the Shell), held as the section above says.

The design kit's revision 03 is such a change. The shipped schemes are built on Graview's identity — paper `#f7f7f2`, ink `#18213a`, muted `#586174`, En Dash navy `#001769` as the light accent, `#9aabff` on a navy ground `#0a0f1f` in the dark — and paint no wash (`wash: "none"`); `TYPOGRAPHY.body` names Montserrat first (never fetched: the host loads it, or the system sans stands in), with three new properties for its weights (`--graview-weight-display`, `-body`, `-label`: 550, 450 and 600 on the framework's face, 600, 400 and 600 on a face a brand names); `h1` and `h2` are tracked at −0.025em; the default radius is 8 px (6 small) where it was 12 (9). A brand that names its own schemes, faces and radius draws exactly as before but for the heading weight (`--graview-weight-display`, 600 where the browser's bold was 700), the two largest headings' tracking and buttons' labels at 600. A brand derived with `brandFromAccent` over the shipped schemes takes the new grounds, panels and inks with its own accent. `system-sans` in a document is the system's own stack as it always was.

The routed face's type is the look too. It is one scale written by the theme as four custom properties — `--graview-text-small`, `--graview-text-body`, `--graview-text-heading` and `--graview-text-title` (0.833, 1, 1.2 and 1.728rem, a minor third from the reader's rem) — whose values a patch may move and whose names are kept; an app's own stylesheet that sets one moves that step wherever the face uses it. Headings take the theme's heading rule (`--graview-font-display`, `--graview-weight-display`), so a brand's own face and weight always win. What a host's page or harness reaches in a derived list is kept and said on the `Compatibility:` line when it moves: a row `li.graview-row` (in `ul.graview-rows`) holding its link `a.graview-row-title` and its glance `span.graview-row-glance`, a search hit the same row as `[data-testid="search-hit"]`, and a group's or a section's heading `h2.graview-group-head`. A row's glance leaves off the field its group is by and a choice the list is narrowed to one value of.

How the app bar lays itself out is the look too. Since it fits its box, it reads its own width and never the screen's (a phone's bar below 640 px of its own), Find is a small box that says its shortcut and is drawn wide while it is used, and the switch draws its icons alone when its words do not fit. What a host's page or harness reaches is kept as it was and said on the `Compatibility:` line when it moves: the test ids (`app-faces`, `app-face-scene`, `app-face-pages`, `app-find`, `app-find-open`, `find-box`, `nav-find`, `app-places-open`, `app-place-current`), the embed's `switch` option (`"words"`, the default, or `"icons"`), and the switch's `data-switch` (what was asked) and `data-switch-drawn` (what is drawn). A host that wants the switch held to its icons asks for `switch: "icons"`; nothing holds it to its words at every width, because a bar too narrow for them would run out of its box. A host whose own bar stands above the embed says what the embed's bar leaves out (`bar: { faces: false, name: false }`, `EmbedBar`): with `faces: false` there is no `app-faces`, with `name: false` no `app-home` and no `app-name`; the places, `app-find-open`, the standing and `profile-button` are drawn as ever, and `bar: true` is the whole bar it always was.

Where the places stand is the look as well (FR-145): on a bar with room after the name, the switch and the tools, the app's primary places stand on the row as words, in their order and never more than six with Home — the one the reader is on always among them — and the rest fold into "More"; with too little room the one control returns; a phone's bar keeps the one control. Which places are primary is the declaration's (`pages.primary`, kinds by name or plural and pictures by title); unsaid, every kind but the ones that support the others (a kind `pages.hide` leaves off the home, a kind of a module drawn only for its keepers, a note pointing at several kinds that nothing points at) stands, with its pictures, and Connections folds. On the scene the bar's places are the scene's (FR-144): "The whole thing" (`app-place-scene:whole`) and each picture (`app-place-scene:<kind>:<as>`), each with the scene's address for it as its `data-place-path` (`/places/overview` for the whole thing, the overview at altitude by its address alone since FR-154; `/places/overview#focus=…&in.view=<as>`). How many stand changes with the width, the brand's face and the app's places, so a harness never counts on it. What is kept, at every width and on both faces, is how a place is reached — one recipe:

1. Every place the bar offers is one element in the embed, `[data-testid="app-place-<key>"]`, carrying its `data-place-path` (the same key and path as before FR-145; a list's `kind:<kind>`, a picture's `place:<kind>:<as>`, the home's `home`, `connections`).
2. If that element is visible, press it (it stands on the row).
3. If not, press `[data-testid="app-places-open"]` — "More" where places stand, the one control where none do, on a phone the page's first line — and press it in `[data-testid="app-places"]`, the list it opens.
4. `[data-testid="app-place-current"]` says the place the reader is on: the one control's words, or the place standing on the row, marked `aria-current="page"`.

The list is grouped as before (`data-place-group`: `home`, `lists`, `pictures`), holding the places that do not stand; `app-places-open` is absent only when every place stands. The places standing on the row are inside `nav[data-testid="app-places-standing"]`.

How a list arranges is the look too: one quiet line under its title — the count in words ("16 tasks", "4 of 16 tasks" where something narrowed it), then "Sort", "Group" and "Filter", each opening a short list (`usePopover("arrange")`), and each condition as words with a ×; a narrow line is the count and one "Arrange". What a host's page or harness reaches is kept and said on the `Compatibility:` line when it moves: the line `[data-testid="<prefix>-bar"]` (`role="group"`, named "Arrange"; the prefix is `arrange` on the derived face and in a lens, `list` on an app's page that says so), the count `<prefix>-count` (with `<prefix>-kept` for "4 of 16"), the words `<prefix>-sort`, `<prefix>-group`, `<prefix>-add` (Filter) and `<prefix>-all` (Arrange) — buttons whose `value` is the chosen sort or group, as the selects' was — and the open list `[data-testid="arrange-list"]`, whose entries are buttons carrying the condition or choice as `data-value` (`due`, `holds:today`, `price:at-most:25000`) and `aria-pressed` for the one chosen; the direction's `<prefix>-direction-asc`/`-desc` and a date group's width `<prefix>-bucket-<day|week|month|year|decade>` are in those lists; a condition is `<prefix>-condition`; a date's day is asked in the list (`<prefix>-ask-day`, `<prefix>-day`, `<prefix>-day-add`). The addresses are as before (`?sort=`, `?group=`, `?filter=`, `?q=`, and the older `?by=`, `?<edge>=`, `?with=`, `?past=1`). Adding a record on a list page is one press, `[data-testid="act-open-<act>"]`, which opens `form-<act>` in place; the form stands open while the list is empty. A list of a kind with a `when` role (`fieldRoles.when`) opens, when its address says nothing, newest first by it at any length; a list of forty records or more otherwise opens by name; and a list of forty or more is sectioned by year or letter under `[data-testid="list-index"]` (each `list-section`); a harness that wants the stored order passes `?sort=`. What a kind opens to in the scene when the app drew it no picture is the look too: going into its district (`#focus=aggregate:<kind>`, a kind with no lens) draws its stop in the box a lens fills — the plural, the count and the description; the creating act first, asked in place; what is overdue or due this week, its problems by rule and what changed since the reader last looked; then a picture its data chooses (a board by its main choice up to 300 records, a calendar where today's month has short records on its main date, else a table of its glance and relations, 50 rows at a time), with the other shape one press away and "Keep as a lens"; from altitude it opens in the panel beside the map a lens opens in (`lens-panel`), one panel at a time, focused as `#overview=1&focus=aggregate:<kind>`, where a single press still lists the district (`district-panel`), which is the seat's `add-lens` (`recipeDraft`, `@graview/tools/draft`). ### The conformance kit

`@graview/core/conformance` ships fixtures: declaration documents with the check findings and tool schemas this framework made of them, and op logs with the snapshot hash each folds to. `conformance()` runs them against this build, or against a build a host hands it, and returns the differences by fixture id. A host runs it before it takes a version.

The fixtures are append-only. `node scripts/conformance-fixtures.mjs` only ever adds a fixture with a new id, and a lock holds the rest. A change to a recorded fixture is an announced difference (`ANNOUNCED`), with the version that made it and what changed.

### The Compatibility line

A pull request that touches a file on one of the five surfaces asks every changeset it adds for a line:

```md
Compatibility: additive — `Operation.via` is a new optional field; ops without it read as before.
```

The line says the surface, whether the change is *additive*, *breaking* or *unchanged*, and for whom. `scripts/require-changeset.mjs` refuses a changeset without one (CI's `changeset` job), and the files that count as each surface are in `scripts/lib/surfaces.mjs`. The line goes into each package's CHANGELOG with the rest of the changeset, so every release lists what it did to compatibility.

### `capabilities()`

```ts
import { capabilities } from "@graview/core";

capabilities();
// { version: "0.1.43", protocol: 1, documentFormats: ["graview-document@1"], formats: { snapshot: 1, op: 2 },
//   shipped: ["FR-06", "FR-11", …] }
```

`shipped` lists the ids of the seams this build ships, by the ids Graview Cloud filed them under. A host retires its interim for a seam when the id appears. A test holds the list to the FR ids the changesets name, so a seam cannot ship unannounced or be announced without shipping.

`FRAMEWORK_VERSION` is the version alone, for a host that records which framework folded a store.
