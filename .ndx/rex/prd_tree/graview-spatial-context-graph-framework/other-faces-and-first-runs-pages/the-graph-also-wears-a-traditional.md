description: "The spatial workbench is a novel way of seeing a context graph; it should not be the only way the graph can be seen. This feature makes the framework produce, from the SAME declaration that drives the scene, a traditional web application: a react-router app with pages — a list page per kind, a record page per node showing its fields and its relationships as ordinary links, forms derived from mutations, problems from invariants, visibility from the permission policy. Ship a couple of default page templates; expose an SDK seam so an installation can bring its own templating, the way lenses already bring their own pictures.\n\nWhy: backwards compatibility with the web interface paradigms people are used to, mobile/responsiveness (the spatial scene is a desktop instrument), and the pitch that you can spin up an entire application by specifying the context graph config plus starter data — and get a deep/cross-linked, relational, auth-scopable interface with both a novel spatial face and a familiar routed face.\n\nARCHITECTURE GUARDRAILS (the expensive wrong turns, named):\n\n- **A new package** (working name @graview/pages), sitting beside @graview/react in the dependency tiers — importing core/layout/tools and primitives' non-scene pieces where they genuinely serve a page, never the Scene. It ships and smoke-installs like the others. Do NOT bolt pages into react (whose one job is the scene binding) or primitives (whose components assume the plane model).\n- **The page registry is the seam**, shaped like the view registry: (kind × page-type) → component, defaults registered first, apps override per cell. That symmetry is the whole SDK story — an author who has registered a view already knows how to register a page. A layout shell (nav, header, brand) is itself a replaceable registration.\n- **This is not the modal reborn.** Jack-in's full-page modal was deliberately deleted in favour of the in-scene zoom; the traditional face is a separate routed SURFACE over the same store, not a return of that modal. The record reading-column patterns from that era are fair salvage; the dialog-over-the-scene architecture is not.\n- **One store, no second path.** Pages read through the same Store/GraphReader and write through the same mutations with the same principal; permission narrowing shows withheld actions disabled with their reasons (the strip's existing honesty, restated on a page). Anything the pages need that requires reaching around the public API is a missing framework seam to fix first — the smoke-install rehearsal is the referee.\n\nTHE ICEBERG, NAMED: forms. A traditional face is mostly forms, and form derivation is today the framework's weakest derivation — argShape handles scalars and node refs, and a structured argument (a union like the household example's constraint spec) is un-askable; the strip now honestly refuses to offer such actions, but a page cannot: \"New agreement\" MUST render. Budget real work for deriving form controls from zod inputs (objects, discriminated unions as type-picker-then-fields, arrays, optionals), and land it in tools/core where the strip's prompts inherit it too. The recent set-hour-cap/set-balance-tolerance split shows the app-level workaround; the pages effort is where the general answer belongs.\n\nPAGE INVENTORY (the defaults that ship): a home/dashboard (standing of the rules, recent activity from the op log, kind index); a list page per kind (label, key fields via field roles, violation marks, links); a record page per node (fields with in-place edit where a mutation writes them, every edge as a link group in both directions, its violations with repairs, its op-log history, its actions as forms); a problems page (violations with repairs); auth-aware nav. Search can wait; SSR can wait; both should be recorded as deferred, not discovered as gaps.\n\nURL INTEROP, concretely: routes derive from the schema (/:plural and /:plural/:id off labels/ids the graph already has), every record page links to its spatial stop (#focus=<id>) and the scene's inspector offers \"open as page\" back; the two faces are one application because the ids are.\n\nVERIFICATION, in this repo's culture: a parity test asserting a record page and its spatial detail derive identical facts (fields, edges, violations, legal actions) from the same store; graview check gains page checks (a route per kind, no orphaned link targets, contrast on the shells); the site-style width/axe harness runs against the default pages at phone widths — mobile is an acceptance criterion, not an aspiration; survey gains the example app's page face.\n\nRelationship to what exists: the derivation machinery is already all there — default views render any kind at three fidelities with zero custom code, affordances derive actions, permissions narrow surfaces. This feature points the same machinery at a router target. The launcher's routing/liveness work and the smoke-install scratch app are the proving grounds; the blank-graph onboarding app (5a35ebdf) is the second consumer; graview-cloud serves this face to mobile tenants by default."
